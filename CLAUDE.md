# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install        # install dependencies
npm run dev        # start dev server (http://localhost:3000)
npm run build      # production build
npm test           # run all tests (vitest)
npx vitest run __tests__/api/sessions.test.ts              # run a single test file
npx vitest run __tests__/api/sessions.test.ts -t "resume"  # run tests matching a name
```

There is no lint or typecheck script; `npm run build` is the type check.

## Environment setup

Copy `.env.example` to `.env.local` and fill in your Supabase credentials. Then, in the Supabase SQL editor, run `supabase/schema.sql` followed by `supabase/seed.sql` (the question bank — without it every session start returns 400), and create a **public** Storage bucket named `avatars` for profile images. (README.md's mention of a `myapp_profile` table is stale — the profile table is `"user"`.)

`INSTRUCTOR_SIGNUP_CODE` (the invite code that grants the instructor role at registration, see "Auth flow" below) must be set to a real, random, per-deployment value — generate one yourself (e.g. `openssl rand -base64 24`) and set it only in each deployment's own environment (`.env.local` locally, Vercel Environment Variables in production, etc.). It must never be committed to the repo, in `.env.example` or anywhere else.

`lib/supabase.ts` accepts either `SUPABASE_URL` or `NEXT_PUBLIC_SUPABASE_URL` and exposes three factories, each returning `null` when its key is missing so routes can answer 500 instead of a confusing Supabase error:

- `getSupabaseClient()` — service-role key preferred, anon fallback. Used by every data route; it bypasses RLS, which is why those routes must derive `user_id` from the token themselves.
- `getSupabaseAuthClient()` — anon key preferred. Only `login` and `refresh`, so Supabase issues/renews a real user session.
- `getSupabaseAdminClient()` — service role, no fallback. Only `register` (`auth.admin.createUser`, which bypasses email confirmation).

Clients are created per call with `persistSession: false` — no singleton, no shared state.

## Architecture

Next.js 14 App Router, Tailwind, Supabase. The product is a requirements-practice app for students; `docs/requirements/requirements.md` is the spec, and its identifiers (`REQ-DL-3.1`, `REQ-PL-2.1`, `REQ-GAM-BL-1`, …) are cited in code comments — read the referenced requirement before changing behavior that a comment ties to one. Code comments also cite GitHub issue numbers (`GitHub #82`, `#120`, `#149`, `#169`, …) for feature-level context.

### Half-connected worlds — read this first

Parts of the app were built against real API routes, parts against localStorage mocks. The wiring-over is in progress, not finished. **Before trusting any data source, grep for who actually reads it.**

**1. Real, tested backend.** API routes + `lib/*Queries.ts` + `supabase/schema.sql` are the real implementation (sessions, answers, feedback, score, titles, activity log, instructor statistics, LLM-graded acceptance-criteria submissions), fully covered by tests. `lib/sessionClient.ts` is the UI's one gateway to the MCQ session routes — same role as `lib/authClient.ts` for auth. The student quiz flow is fully migrated: `app/activities/[slug]/page.tsx`, `app/activities/[slug]/play/page.tsx`, `app/dashboard/log/page.tsx`, and the session lists on `app/dashboard/page.tsx` / `app/activities/page.tsx` all go through `sessionClient`. The slug↔`activity_type` mapping is declared in exactly one place: `ActivityDefinition.activityType` in `lib/activityContent.ts`.

`write-acceptance-criteria` is a fourth, structurally different activity (GitHub #149, REQ-FU-2) — free-text and LLM-graded rather than multiple-choice — but its *session* is real `session_log` now, the same table and lifecycle Type A uses: `activity_type = 'WRITE_ACCEPTANCE_CRITERIA'`, `session_to_user_story` in place of `session_to_question`, `submission.session_id` in place of `answered_question_log`, and the same abandon route (`POST /api/sessions/{id}/abandon`) and completed-attempts route (`GET /api/sessions/completed`) Type A already had — nothing AC-specific needed to be written for either. `lib/acceptanceCriteriaQueries.ts` mirrors `lib/sessionQueries.ts`'s role (`loadSessionStories`/`loadSessionSubmissions`/`nextUnansweredStoryPosition`, the last delegating to `nextUnansweredPosition` itself rather than reimplementing it), and `lib/acceptanceCriteriaClient.ts` mirrors `sessionClient.ts`'s. The page is split the same way as Type A: `app/activities/write-acceptance-criteria/page.tsx` (landing — Start/Resume-Abandon/previous-attempts) and `.../play/page.tsx` (the writing/feedback/summary flow), through `startOrResumeAcceptanceCriteriaSession`/`loadCurrentAcceptanceCriteriaSession`/`submitAcceptanceCriteria`. `session_to_user_story` and `submission.session_id` existed in `supabase/schema.sql` for a while before this wiring landed — an earlier, incompatible attempt at a real session (`ac_session`/`ac_session_story` tables, never migrated into `schema.sql`) is gone; if you find a reference to those table names anywhere, it predates this fix and is stale. `ActivitySlug` in `lib/activityContent.ts` includes this activity so `ActivityCard`/`activityLogTypes.ts` can type all four activities uniformly — see the comment there before assuming it behaves exactly like the two Type A ones (it still has no question bank or difficulty progression).

**2. The leveling mock.** `lib/activityStore.ts` is still a localStorage mock (`rc_activity_progress_v1`) of the leveling/history side of the domain — current difficulty level, best score, earned title. **Nothing writes to it any more**: `startSession`/`abandonSession`/`answerQuestion`/`currentQuestionId`/`getBestScore` have no callers at all since the play flow moved to the API, so every value it can return is frozen at its default — `level` is always `1`, `getTitle` always `'Not yet started'`, `getHighestTitleOverall()` always `null`, `state.inProgress` always `null`. Treat anything it returns as a lie, not as stale data.

It is now read by only two places, and both are showing those frozen values: `app/dashboard/page.tsx` (`getActivityState`, whose "Continue where you left off" panel is therefore permanently empty even with a real session running) and `components/AppShell.tsx` (`getHighestTitleOverall`, falling back to `'Getting started'`). `app/activities/page.tsx` was the third and no longer touches it — GitHub #272 was exactly this bug surfacing as misleading card text, and it now reads `loadStudentTitles` for the title and the in-progress `SessionListEntry` for the level. `app/activities/[slug]/page.tsx` never touched it either: "is something running?" there comes only from `loadCurrentSession`. Migrating the last two readers the same way is what's left; note `activityStore.ts:128` also uses a `0.8` pass threshold against `sessionRules`' `PASS_RATIO = 0.75`.

Card status text has one source: `lib/activityCardStatus.ts` (`deriveActivityCardStatus` + `activityCardStatusLabel`). Its two-slot rule is load-bearing — the mastery **title** slot renders only a genuinely earned title (`StudentTitle.difficultyLevel !== null`, never string-matched against the server's `'Not yet started'`), and the **status** line says what the next click does. Putting a placeholder back into the title slot re-creates #272. `deriveActivityCardStatus` has four states, ranked by precedence: a running session (`'in-progress'`) always wins since that's what the next click resumes; then `'mastered'` (every difficulty level passed — `highestPassedLevel === MAX_DIFFICULTY_LEVEL`), which outranks a plain `'best-score'` as strictly more complete information about the same history; then `'not-attempted'`.

**Courses — real, but a separate, parallel structure (REQ-DL-5, GitHub #241/#242).** `course` and `student_course` tables (`supabase/schema.sql`), `lib/courseQueries.ts`, and two real clients — `lib/courseClient.ts` (instructor) and `lib/studentCourseClient.ts` (student) — back a full create/browse/join/roster flow: `app/instructor/courses/page.tsx` (list + `CreateCourseModal`, a button-triggered popup — GitHub #241 follow-up, replacing the page's old permanently visible inline form) and `app/instructor/courses/[id]/page.tsx` (roster, rename, enroll/unenroll, join-code display) on the instructor side; `app/courses/page.tsx` (`StudentCourseCard`, browse-by-name/professor + join-by-code) and `components/MyCoursesSection.tsx` (on `app/profile/page.tsx`) on the student side. A course has a nullable, unique `course_code` — `lib/courseQueries.ts`'s `findOwnedCourse` is a reusable 404-then-403 ownership check other instructor routes don't have. The join code itself is never sent to a browsing student (`JoinableCourse` in `lib/courseTypes.ts` has no `code` field) — only `POST /api/courses/join` resolves it, server-side. **It is not wired into anything else yet**: `GET /api/instructor/statistics`, `/sessions`, and `/activities` (and the instructor dashboard/roster pages that call them) are still class-wide with no `courseId` filter — the "no professor-to-quiz/-student ownership in the schema" gap those routes' own comments describe is now only half true (the schema has `course`; these routes just don't consume it). The one cross-link that exists: `components/AddStudentForm.tsx` reuses `loadInstructorStudents` (the whole-class roster) as its enrollment search, not a course-scoped query. Ignore in-code comments in `lib/courseQueries.ts` and `app/api/courses/join/route.ts` that mention a `lib/mockCourses.ts` still backing `StudentCourseCard` — that file doesn't exist; the component already calls the real `studentCourseClient`. Per-course enrollment is a real round trip too: `courseClient.ts`'s `addStudentToCourse`/`removeStudentFromCourse` back `POST`/`DELETE /api/instructor/courses/{id}/students[/…]`, and `exportCourseReport` backs `GET /api/instructor/courses/{id}/export` (REQ-PL-3.4.3) — a depersonalized CSV (`lib/csv.ts`'s `toCsv`, no student name column) of every `session_log` attempt by that course's roster, reusing `loadStudentActivityForIds` rather than a new query. Unenrollment has two routes, not one: the instructor-driven `DELETE /api/instructor/courses/{id}/students/{studentId}` above, and a self-service `DELETE /api/courses/{courseId}/enrollment` (GitHub #325) a student calls on themselves, scoped to their own token — deliberately not idempotent like the instructor route, since it names a specific caller-owned resource and 404s on an unknown course or a caller who was never enrolled. Instructors can also delete the whole course — `DELETE /api/instructor/courses/{id}` (GitHub #326/#327) reuses the same `authorizeCourse`/`findOwnedCourse` 404-then-403 dance `GET`/`PATCH` on that route already share, counts the roster before deleting, and returns `{ courseId, unenrolledCount }`. `fk_student_course_course` is `ON DELETE CASCADE`, so enrollments disappear in the same transaction; nothing else references `course_id` (`session_log` and `question` don't have one), so scores, titles and activity history survive a course's deletion — only the course, its join code, and its CSV export are gone. `components/DeleteCourseModal.tsx` states that distinction before the instructor confirms, and defaults focus to Cancel.

**The leaderboard — real now.** `GET /api/courses/{courseId}/leaderboard` (`lib/leaderboardQueries.ts`'s `computeCourseLeaderboard`) ranks every student in `student_course` — not just those who've attempted something, the opposite of `loadAllStudentActivity`'s known "roster derived from attempts" gap — by the exact same `sumBestScores` reducer `computeStudentScore` (`lib/scoreQueries.ts`) uses for the sidebar score pill, so the two numbers can't drift. Only `username`/`avatar_url` leave `"user"`, via an `!inner` join filtered to `role = 'student'` (backed by `ix_user_role`, the same pattern `loadAllStudentActivity`'s `STUDENT_EMBED` uses) — no name/age/semester. Standard competition ranking (ties share a rank, the next rank skips) with username as the deterministic tiebreaker. Authorization is enrollment, not ownership or role: the route 404s an unknown `courseId` before checking anything else, then 403s a caller who isn't themselves in `student_course` for it — the one genuinely new cross-user authorization rule in the app, since the only other student-callable cross-user read, `GET /api/courses` (`listJoinableCourses`), discloses course metadata but never another student's identity or score.

`app/leaderboard/page.tsx` and the dashboard's `components/LeaderboardPreview.tsx` both read this route through `lib/studentCourseClient.ts`'s `loadCourseLeaderboard` — cached in `lib/leaderboardStore.ts` (courseId-keyed, same shape as the other client caches) so the two share one cache entry per course. `rankChange` is still never part of the server response (`lib/leaderboardTypes.ts`'s own doc on `LeaderboardEntry`) — `loadCourseLeaderboard` attaches it from `lib/previousRankStore.ts`'s last-recorded per-course rank snapshot (`getPreviousRanks`/`withRankChange`), and each page records the new snapshot itself, in a `useEffect` keyed on the fetched entries so the write happens strictly *after* that render used the *old* snapshot — writing first would make a delta compare a fetch against itself. That store's own header names the honest limits (per device, per browser, wiped on logout) and a zero-migration alternative for later (replay `sumBestScores` over `session_log` filtered to `ended_at < T`, no new table needed). The leaderboard cache has no automatic invalidation when *another* student's score changes it — same staleness `loadInstructorActivities` documents — so `app/leaderboard/page.tsx` has a manual Refresh button, and the play page's `handleFinishSummary` blanket-clears the whole leaderboard cache (not a single courseId — the page doesn't know which of the student's courses to target) whenever the student's *own* score changes on session completion. Course lists for both the switcher and the preview come from `loadMyLeaderboardCourses` (`lib/studentCourseClient.ts`, GitHub #328) — the `alreadyMember`-filtered slice of `loadJoinableCourses`, cached session-scoped in its own store (`lib/leaderboardCoursesStore.ts`) so revisiting either view within the same tab session doesn't re-fetch the course list; `loadJoinableCourses` itself stays uncached, since `app/courses/page.tsx`/`MyCoursesSection` need a just-joined course to appear without waiting out a stale session cache. `lib/leaderboardStore.ts` and `lib/leaderboardCoursesStore.ts` are deliberately `sessionStorage`, not `localStorage` (GitHub #329) — unlike every other client cache in this app, a stale leaderboard entry must not survive an app restart, so a fresh tab always gets exactly one real fetch regardless of what a previous session left cached. `app/leaderboard/page.tsx`'s Refresh button forces both caches (course list and entries) together, since course membership can itself have changed mid-session.

**A classmate's public profile — real now too.** `GET /api/students/{studentId}/public-profile` (`app/students/[id]/page.tsx`, reached from a leaderboard/preview username) is real, and `lib/mockLeaderboard.ts` — the last of the leaderboard feature's Phase-1 mocks — is deleted. This route deliberately does **not** reuse the `/api/students/{studentId}/*` preamble every other route under that path shares (`score`, `titles`, `activities`, `history`): those all 403 the instant `studentId` isn't the caller's own id, by design, which is exactly wrong here — the route exists to serve someone *else's* data. Its authorization is instead "do the caller and the target share a course" (`student_course` intersection), built on `isEnrolledInAnyCourse` (`lib/courseQueries.ts`) — the same shared helper `GET /api/courses/{courseId}/leaderboard`'s own enrollment check now uses too (there with a single-course list, here with the target's full course list via `getEnrolledCourseIds`), so "enrolled" can't drift between the two routes. 404-then-403 ordering: unknown `studentId` → 404; a non-student target (an instructor has no public profile) → 403; no shared course → 403. The response is exactly `{ username, avatarUrl, biography, score, titles }` — `score`/`titles` are `computeStudentScore`/`computeStudentTitles`'s own numbers, not re-derived, and `role` is selected server-side only to decide the 403, never returned. `app/students/[id]/page.tsx` reads this through `lib/sessionClient.ts`'s `loadPublicStudentProfile` (uncached, same reasoning as `loadStudentTitles`) for the peer branch; the `isSelf` branch is unchanged, still reading `loadStudentScore`/`loadStudentTitles` directly. Shared display components across the leaderboard screens: `components/LeaderboardTable.tsx`, `LeaderboardCourseSwitcher.tsx`, `LeaderboardSkeleton.tsx`, `LeaderboardRankBadge.tsx`, `RankChangeIndicator.tsx`, `Pagination.tsx`, and `components/Avatar.tsx` (extracted from `AppShell.tsx`/`StudentDetailHeader.tsx` duplication; a fixed `size` set, not a free className, so call sites can't drift into slightly different circles — deliberately *not* used by `app/profile/page.tsx`, whose avatar is an upload-button, not a display avatar).

Most of the front-end-first instructor work that used to sit in a third "UI-only mock arrays" world is gone: `lib/mockQuestions.ts` (`MOCK_QUESTIONS`) was replaced by the question-bank routes (GitHub #170/#121/#158). (`lib/mockStudentActivity.ts` was another one and is gone too — the instructor dashboard and roster now read `GET /api/instructor/activities`.)

**Question Catalogs — "Quizzes" (GitHub #347/#348) and "Question Catalogs" (GitHub #359) are the same feature, not two.** A "catalog" is exactly what this codebase already calls a "quiz": a named, ownable row in the `activity_type` lookup table (`quiz_name`, `description`, `creator_id`, GitHub #347), with every `question` whose `activity_type` column points at it. `POST /api/activities/types` creates one (`lib/quizClient.ts`'s `createQuiz`); `GET /api/instructor/quizzes` (`lib/activityTypeQueries.ts`'s `listQuizzesWithAuthorAndCount`) browses every catalog in the system, any author — catalogs are shared, same as courses are not. When GitHub #359 asked for a "Question Catalog" that replaces the old flat Question Bank page, the right call was to extend this existing structure rather than add a parallel `question_catalog` table: the flat Question Bank page (`app/instructor/questions/page.tsx`, its `GET /api/instructor/questions` list route, and `lib/instructorQuestionsStore.ts`) is deleted, and the `instructor-quizzes` nav item (still that key internally — only its label changed) now reads "Question Catalogs" and sits where "Question Bank" used to. Clicking a catalog on `app/instructor/quizzes/page.tsx` opens `app/instructor/quizzes/[activityType]/page.tsx` — read-only by default (`GET /api/instructor/quizzes/{activityType}`, `lib/activityTypeQueries.ts`'s `getQuizByActivityType` + `listCatalogQuestions`, every question in the catalog regardless of author), an "Edit" toggle away from add/edit/delete on the caller's own questions (`POST`/`PATCH`/`DELETE /api/instructor/questions[/…]`; `DELETE` is new in GitHub #359 and refuses with 409 if the question already has a `session_to_question` row, since `question_to_answer`/`answered_question_log`'s FKs to `question`/`answer` have no `ON DELETE` clause). `QuestionFormModal`'s quiz picker used to be a hardcoded two-item list (only the original two Type A activity types) — GitHub #359 replaced it with a `quizOptions` prop, since a hardcoded list could never target a custom catalog; the catalog detail page passes its own single catalog, effectively locking the field. A question has exactly one `activity_type` column, not a join table, so a catalog's edit mode can never leak into another catalog — that isolation falls out of the schema, not route-level enforcement. The narrower, still-unused `GET /api/instructor/quizzes/:activityType/:difficultyLevel/questions` (below) is a different, pre-existing route this didn't touch. The genuinely different "assemble a quiz from one or more catalogs, scoped to a course" feature this paragraph used to flag as undesigned is now built — as its own entity, not a third meaning bolted onto `activity_type` — see the next paragraph.

**Assembled quizzes (GitHub #360) are a third, deliberately separate "quiz" concept — not a rename, not a merge.** Where a catalog (`activity_type`) *is* a flat, leveled pool of questions, an `assembled_quiz` (`supabase/schema.sql`) *composes* one or more catalogs for exactly one course: `assembled_quiz(assembled_quiz_id, quiz_name, description, course_id, creator_id, created_at)` plus the m:n join `assembled_quiz_catalog(assembled_quiz_id, activity_type)`, both new tables, RLS-enabled with no policies like `question`/`course`. `course_id` is `NOT NULL` with `ON DELETE CASCADE` — an assembled quiz composed for a course has no meaning once that course is gone, same reasoning as `student_course`'s cascade. This was a deliberate decision, not the only option: `activity_type` already *could* have grown a `course_id` and a catalog-reference table, but doing so would have broken the "one `activity_type` = one flat leveled pool" invariant every other piece of the app relies on (`session_log.activity_type`, `title_definition`, `question.activity_type` all key on that atomicity) — see the previous paragraph's "own name" note, written in anticipation of exactly this issue. `lib/assembledQuizQueries.ts` holds the query layer: `createAssembledQuiz` (insert quiz + link rows, deleting the quiz row on a link-insert failure — no transaction, same rollback-by-hand pattern `POST /api/instructor/questions` uses), `listAssembledQuizzesForInstructor` (scoped to `creator_id`, *not* shared the way catalogs are — a quiz is built for one of the caller's own courses, and courses aren't shared between instructors either), and the random-draw pair `loadCatalogQuestionPool`/`pickRandomQuestions`. The draw is dynamic, not materialized at creation time: no per-level question set is stored anywhere, so editing a linked catalog's questions later is reflected immediately, the same "always current" property the catalog detail page (GitHub #359) already has. **Nothing calls the draw functions in a live session yet** — no student-facing session/play route exists for an assembled quiz, so it cannot actually be taken today; that's the natural next issue. Create/browse (`POST`/`GET /api/instructor/assembled-quizzes`) and the instructor UI at `app/instructor/assembled-quizzes/page.tsx` (`lib/assembledQuizClient.ts`) are reachable from their own "Quizzes" nav item — deliberately a *different* sidebar entry from "Question Catalogs" (`instructor-quizzes`), sitting right after it, so the two "quiz" concepts this section distinguishes stay visually distinct too. Both `page.tsx` create flows (this one and `instructor-quizzes`' catalog list) are button-triggered popups (`CreateQuizModal`/`CreateCatalogModal`), not permanently visible inline forms — same for course creation (`CreateCourseModal`, `app/instructor/courses/page.tsx`); all three, plus `ConfirmModal` (below), share `components/useModalDismiss.ts` for the focus-trap/Escape/backdrop-click/focus-return wiring rather than each hand-rolling it independently the way the older modals (`QuestionFormModal`, `EditCourseModal`, `DeleteCourseModal`, `DeleteQuestionModal`) still do — those weren't retrofitted, so both patterns coexist; copy whichever a new modal is structurally closer to.

**Managing an assembled quiz's composition (GitHub #361) — "displayed as copies of the originals" is an exclusion list, not duplicated rows.** A quiz still references its ORIGINAL catalogs via `assembled_quiz_catalog`; `quiz_excluded_question(assembled_quiz_id, question_id)` (`supabase/schema.sql`, both FKs `ON DELETE CASCADE` — unlike `question_to_answer`/`answered_question_log`'s lack of one, there's no student history here to protect) is the only new table, and it is the *entire* mechanism: excluding a question for one quiz writes exactly one row there and touches `question`/`answer` never, which is what makes the original catalog provably unaffected — by construction, not by convention. The alternative (cloning question/answer rows per quiz) was rejected because it would need its own sync story the moment the original catalog changes; the exclusion list needs none, since `lib/assembledQuizQueries.ts`'s `getQuizComposition`/`loadCatalogQuestionPool` always compute "what's active" by re-reading the catalogs' current questions minus the current exclusion set, live, on every call. Routes live under `/api/instructor/assembled-quizzes/{quizId}/…`, not `/api/instructor/quizzes/{quizId}/…` — GitHub #359's catalog detail route already owns `/api/instructor/quizzes/[activityType]`, and Next.js rejects two differently-named dynamic segments (`[activityType]` vs `[quizId]`) at the same route position, so this nesting is required, not stylistic. `findOwnedAssembledQuiz` (`lib/assembledQuizQueries.ts`) is `lib/courseQueries.ts`'s `findOwnedCourse` pattern reused for quizzes — every composition route's ownership check goes through it. `GET /api/instructor/assembled-quizzes/{quizId}` (`app/instructor/assembled-quizzes/[quizId]/page.tsx`) returns the quiz's linked catalogs with a *genuinely* active count (total minus this quiz's own exclusions, never another quiz's or the catalog's own) plus per-level coverage against `QUESTIONS_PER_SESSION` — the page turns any level below that into a visible warning banner *before* a student could ever hit a level with too few questions to draw a round, since there is still no live session route to catch it downstream. Excluding/including one question happens on `app/instructor/assembled-quizzes/[quizId]/catalogs/[activityType]/page.tsx` — the catalog "as it applies to this quiz", read-only over the question content itself (no edit/delete affordance renders there at all; that only exists on the real catalog, GitHub #359) with excluded rows grayed out and badged rather than hidden, so re-including one is a single click away. Deleting a quiz (`DELETE /api/instructor/assembled-quizzes/{quizId}`) is a plain hard delete, not a soft one: no session ever references an `assembled_quiz` (`session_log` only ever points at a catalog's `activity_type`, and has no `assembled_quiz_id` column), so as of today there is no attempt history a delete could destroy — `assembled_quiz_catalog` and `quiz_excluded_question` cascade with it. If a future issue wires up real student attempts against an assembled quiz, *that* issue is what needs to revisit this delete's behavior, not this one. `ConfirmModal` (`components/ConfirmModal.tsx`) backs both this delete and "remove a catalog from a quiz" — the first shared (not just copied) confirmation dialog in the app, justified once a second near-identical one was needed at the same time; `DeleteCourseModal`/`DeleteQuestionModal` predate it and weren't migrated.

One instance of that third world is still very much alive, though: `app/instructor/students/[id]/page.tsx` (the per-student detail page, GitHub #127) reads `lib/mockStudentAttempts.ts`'s `getMockStudentAttempts()` — a fixed, fabricated attempt history — regardless of which student was actually clicked; the `studentId` param and the `MOCK_CLASS_AVERAGE` constant on that page aren't wired to anything real yet. `components/StudentScoreChart.tsx`, `StudentActivityBreakdown.tsx`, and `lib/studentAttemptMetrics.ts` all consume this same mock shape (`StudentAttemptDetail`). `lib/mockStudentAttempts.ts`'s own header comment describes the shape a real per-student endpoint would need to return so those consumers keep working unchanged.

Also dead or unwired, so grep before assuming:
- `lib/activityContent.ts`'s `questionBank` (and `getQuestion`/`questionsForLevel`) is **not** used for gameplay — the play page gets prompts, options, and scoring from the server. `activityContent.ts` is still live for display-only fields (`name`, `summary`, `instructions`, `category`, `titles`) and the slug↔activityType mapping.
- `GET /api/activities/:activityType/questions` and `GET /api/questions/:questionId/options` require a valid bearer token (any authenticated user, not instructor-only) but are otherwise unchanged; no page calls either yet.
- `requireInstructor` in `lib/instructorAuth.ts` (GitHub #169) guards every `/api/instructor/*` route (activities, sessions, statistics, students/{id}/history, llm-config, questions, user-stories, courses, quizzes, acceptance-criteria/*, …). Its docblock contains the exact usage snippet any further instructor route should copy — in particular the 403-with-no-body branch.
- `GET /api/instructor/quizzes/:activityType/:difficultyLevel/questions` is a narrower read path than the catalog detail route above: it scopes to one `(activityType, difficultyLevel)` pair instead of the whole catalog, and returns 403-no-body (not an empty list) when the instructor owns none of that pair's questions, vs. 404 when the pair matches no questions at all — the catalog detail route returns every question in the catalog regardless of author instead of 403ing a non-owner. No client wrapper or UI page calls it yet — it's still dead code, added ahead of whatever instructor screen ends up using it.
- `user_story`, `submission`, and `instructor_llm_config` tables (REQ-FU-2, "Write Acceptance Criteria") exist in `supabase/schema.sql`, and `POST /api/activities/write-acceptance-criteria/submissions` calls `getLLMProvider` (`lib/llm/factory.ts`) against them — see world 1 above. `submission.llm_score`/`llm_feedback`/`llm_provider`/`graded_at` are nullable for the same "write before disclose" reason as `answered_question_log`: the route inserts the row at submit time, then fills in the grading result after the LLM call returns; a crash in between leaves an ungraded row rather than a graded answer that was never recorded. `instructor_llm_config.api_key` is masked by construction: `POST /api/instructor/llm-config`'s `CONFIG_COLUMNS` never selects it back, and `uq_instructor_llm_config_one_active` is a *global* partial unique index (not per-instructor) — at most one config is active across the whole app. There is no `GET /api/instructor/llm-config` yet, so `components/LLMProviderSettingsForm.tsx` still reads/writes through the localStorage-backed mock in `lib/instructorLlmConfigClient.ts` (its header comment documents the gap) even though the real `POST` route exists and is tested — another two-worlds split within a single feature.
- `GET /api/instructor/acceptance-criteria/statistics` (GitHub #152, `lib/acceptanceCriteriaStatisticsQueries.ts`'s `computeAcceptanceCriteriaStatistics`) is real and tested — class-wide submission-count/average/pass-rate aggregates for the AC activity, guarded by `requireInstructor` like everything else instructor-facing. No per-student breakdown; that's a separate route.
- The question bank's `activity_type` columns are now FK-constrained against a real `activity_type` lookup table (GitHub #122/#123), not free text — `lib/activityTypes.ts`'s "Open point: the DB does not enforce this set yet" comment predates that migration and is stale.
- `question.user_id` (GitHub #201) records which instructor authored a question, the same way `user_story.creator_id` does for `GET /api/instructor/user-stories` (GitHub #225). Both columns are nullable, and neither `supabase/seed.sql`'s `question` nor (as far as the app can create one) any `user_story` row is ever inserted with an owner. Unlike `user_story.creator_id`, `question.user_id` no longer gates what a page can *see* — the catalog detail page (GitHub #359) shows every question in a catalog regardless of owner, since catalogs are shared — it only gates what a page renders *edit/delete icons* for: `ownerId !== null && ownerId === caller` on each row, matching the 403 `PATCH`/`DELETE /api/instructor/questions/{id}` already enforce server-side.

### Auth flow

`lib/authClient.ts` is the only place the UI talks to auth routes. It stores both the Supabase `access_token` and `refresh_token` in localStorage (register additionally signs in, since the admin API returns a user but no session). `components/UserProvider.tsx`'s `useUser()` is the single source of truth for the token plus the signed-in profile, mounted once in `app/layout.tsx`.

Session renewal is deliberately two-pronged and there is **no guest/placeholder state**: `UserProvider` refreshes proactively on a 45-minute interval, and reactively when `/api/profile` answers 401 — only if `refreshAccessToken()` also fails is the session cleared and `token` dropped to null. A transient fetch error is explicitly *not* treated as an invalid session; keep that distinction if you touch `refresh()`.

Pages gate on role via `lib/useRequireRole.ts` (`useRequireRole('student' | 'instructor')`, GitHub #82). Callers must return `null` while `!authorized` — the redirect happens in an effect, so rendering early flashes the wrong page. The two roles are asymmetric about a missing profile row (normal right after registration): `'student'` lets it through, `'instructor'` does not and redirects to `/profile`. Treat a page's required role as load-bearing — it's what keeps a student off `/instructor/*` and an instructor out of the quiz-taking flow under `/activities/*`.

Instructor role assignment happens in `app/api/auth/register/route.ts`: the request's `instructorCode` is compared **server-side only** against the `INSTRUCTOR_SIGNUP_CODE` environment variable, written into the auth user's metadata (the `"user"` profile row doesn't exist until the profile form is submitted, where `app/api/profile/route.ts` reads the role back out). `INSTRUCTOR_SIGNUP_CODE` must never be hardcoded or committed (GitHub #280) — an unset, empty, or `CHANGE-ME`-prefixed value makes any instructor signup attempt fail with a 500 rather than silently falling back to a built-in default.

Every protected API route then repeats its own preamble: read `Authorization: Bearer …`, `supabase.auth.getUser(token)`, and derive `user_id` from the result — **never** from the body, query string, or path. The `/api/students/{studentId}/*` routes compare the path param against the token's user and 403 on mismatch (no instructor exception on any of them today).

### Session model (the core domain)

- **One in-progress session per (user, activity_type)**, enforced by the partial unique index `uq_session_log_one_active`. `POST /api/sessions` is therefore idempotent: it returns the existing session with `resumed: true` (200) instead of creating a second one, and treats a `23505` race as "someone else started it". "Start" and "resume" are the same call.
- **The current question is derived, never stored.** It is the lowest `position` in `session_to_question` without a row in `answered_question_log` (`nextUnansweredPosition` in `lib/sessionQueries.ts`). Do not add a `current_question_index` column — the absence of a mutable pointer is what makes multi-device resume conflict-free, and it's why `GET /api/sessions/current` is a pure read with nothing to merge.
- **Write before disclose.** `POST /api/sessions/{id}/answers` commits the answer first and reveals `correct`/`explanation` second; `POST .../feedback` only serves a solution for an option already present in `answered_question_log`. Otherwise the endpoints become an oracle for trying options until one is right.
- **Scores roll up in the database.** The `trg_answered_question_log_score` trigger adds to `session_log.cumulative_score` inside the insert's transaction; routes re-read the row afterwards rather than computing the total locally.
- **Column visibility is a query-level concern.** `SESSION_QUESTION_COLUMNS` in `lib/sessionQueries.ts` deliberately omits `is_correct` and `explanation`; only `loadQuestionOptions` (feedback path) selects them. Keep new queries on that split.
- **Option order is shuffled server-side** with `lib/shuffleArray.ts` (Fisher-Yates, not a `sort()` comparator — the biased-comparator version was a real bug, see `__tests__/lib/shuffleArray.test.ts`).
- **A new session starts one level past the highest the student has passed for that activity type**, not always at `START_DIFFICULTY_LEVEL`. `POST /api/sessions` computes this via `findStartDifficultyLevel` (`lib/sessionQueries.ts`), which reduces the student's `session_log` rows with `highestPassedLevelByType` and feeds the result to `nextDifficultyLevel` (both in `lib/sessionRules.ts`) — `min(highestPassed + 1, MAX_DIFFICULTY_LEVEL)`, or `START_DIFFICULTY_LEVEL` if nothing has been passed yet. `highestPassedLevelByType` is also what `lib/titleQueries.ts`'s `computeStudentTitles` reduces over, so a student's title and their next session's difficulty can't disagree. `nextDifficultyLevel` is reused client-side too, by `app/activities/page.tsx`, to show the level a card's next click will actually start at (falling back to a running session's own `difficulty_level` when one exists) instead of a hardcoded level-1 pill that never advanced — see `activityCardStatus.ts`'s `'mastered'` status below. `session_log.difficulty_level` has a `CHECK (difficulty_level BETWEEN 1 AND 3)` constraint mirroring `question`/`user_story`/`title_definition`'s, added after it was noticed missing.
- `lib/sessionRules.ts` holds the shared constants (`QUESTIONS_PER_SESSION = 4`, `START_DIFFICULTY_LEVEL = 1`, `MAX_DIFFICULTY_LEVEL = 3`, `PASS_RATIO = 0.75`, `SESSION_COLUMNS`, `SESSION_STATUSES`) so routes cannot drift apart. Partial credit is a known gap: `scoreForAnswer` is all-or-nothing until `answer` gains a score column.
- Gamification is derived, not stored: `lib/scoreQueries.ts` sums the best *passing* score per (activity_type, difficulty_level); `lib/titleQueries.ts` looks up `title_definition` by the highest passed level per activity type. Nothing about score or title lives on the student row.
- **The "new title earned" toast (REQ-GAM-PL-2.4/2.5) diffs two client-side snapshots, not a server flag.** `app/activities/[slug]/play/page.tsx` fetches `loadStudentTitles` once on mount (`titleAtStart`, captured before the session can possibly finish) and again after a completed session passes; a title only counts as newly earned if the post-session level beats `titleAtStart` (`null` counts as "nothing passed yet"). This is what tells a genuine first-time pass apart from a retake of an already-mastered level — the server has no "was this title new" concept to ask instead. `SessionSummaryScreen`'s optional `titleNotification` prop renders the toast.

### Reading sessions: which route answers which question

Five read endpoints look similar and are not interchangeable — pick by the question being asked, and keep new ones on the same split:

| Route | Question it answers | Empty result |
|---|---|---|
| `GET /api/sessions?status=…` | "What did I do lately", one status, all activity types | `200` `[]` |
| `GET /api/sessions/current?activityType=` | "Resume this activity" — session + questions + answers so far | `200` with `session: null` |
| `GET /api/sessions/in-progress[?activityType=]` | "Is something running?" — no questions/prompts | `404` *with* activityType, `200` `[]` without |
| `GET /api/sessions/completed?activityType=` | "How did I do at this activity" — attempt history | `200` `[]` |
| `GET /api/students/{id}/activities` | Full timeline: every status, every activity type, merged | `200` `[]` |
| `GET /api/instructor/activities` | Same timeline, but class-wide, `+ studentId`/`studentName` | `200` `[]` |

(`GET /api/students/{id}/history` is the completed-only, cross-activity variant of the second-to-last one, per REQ-PL-3.1. `GET /api/instructor/students/{id}/history` is that same route's instructor-facing counterpart — identical columns and ordering, gated by `requireInstructor` instead of a `studentId === caller` check, and its own 404 for an unknown `studentId` since the caller didn't just authenticate as them.)

The instructor route is the one read that deliberately returns rows the caller doesn't own, which is why `requireInstructor` runs before any query and why its `loadAllStudentActivity` filters the joined `"user"` row on `role = 'student'` with an **inner** join — a non-inner join would null the embed instead of dropping the row, and instructors would appear in their own report. Only students who have attempted something appear at all; the roster is derived from attempts, so an enrolled student with zero sessions is invisible (known gap, separate story). `GET /api/instructor/sessions` and `GET /api/instructor/statistics` (class average + pass rate per quiz, `lib/quizStatisticsQueries.ts`, GitHub #114) are guarded the same way; both currently treat "every quiz" as every row in the `activity_type` table and "every student" as every `role = 'student'` account, with no `courseId` filter (same gap as #115's "students of the current prof") — this is a routes-don't-consume-it gap, not a schema gap: `course`/`student_course` (REQ-DL-5, see the Courses paragraph above) already model instructor-owned classes, these routes just don't scope by them yet.

### Client-side caching

Eleven stores — `lib/scoreStore.ts`, `completedSessionsStore.ts`, `completedAttemptsStore.ts`, `activityLogStore.ts`, `instructorActivityStore.ts`, `instructorStudentsStore.ts`, `acceptanceCriteriaSubmissionsStore.ts`, `instructorLlmConfigStore.ts`, `leaderboardStore.ts`, `leaderboardCoursesStore.ts`, and `previousRankStore.ts` — are a *different* kind of web-storage use from `activityStore.ts`: not mocks, but caches in front of real API calls. All share one shape: a versioned key, SSR-guarded read/write, only typed getters/setters exported (never the raw store), keyed by `studentId`/`instructorId` — `completedAttemptsStore` additionally by `activityType`, `instructorLlmConfigStore` by `provider`+`model`, `leaderboardStore` by `courseId`. `sessionClient`'s (and `studentCourseClient`'s) loaders take an optional id to opt into the cache and a `forceRefresh` flag to bypass and re-cache it. Copy this shape for any new cache, and add a `clearCached…()` to it (see below). Eight of the eleven are `localStorage`; `leaderboardStore` and `leaderboardCoursesStore` are `sessionStorage` (see the leaderboard paragraph above for why) — `previousRankStore` stays `localStorage` despite living in the same feature, since a rank *delta* is only meaningful measured against the last real visit, restart or not. (`lib/instructorQuestionsStore.ts` was a twelfth, fronting the now-deleted flat Question Bank page's `GET /api/instructor/questions` — removed in GitHub #359 along with that page, since the catalog detail page it was replaced by isn't cached; see the Question Catalogs paragraph above.)

The invalidation rule differs: score and completed-sessions only change when a session *completes* (the play page's `handleContinue` refreshes them there), but `activityLogStore` also contains in-progress and abandoned sessions — anything that starts, answers, or abandons must `forceRefresh` it too. `instructorStudentsStore` and `acceptanceCriteriaSubmissionsStore` need no invalidation at all (their own header comments say why).

`loadInstructorActivities` (GitHub #176) *is* cache-first, via `instructorActivityStore.ts` keyed by `instructorId` — but unlike the student-scoped stores, nothing the instructor's own tab does can invalidate it, since the class-wide list changes whenever *any* student answers something and the instructor's tab never learns about that. Its only invalidation is manual: the instructor dashboard's Refresh button (`app/instructor/page.tsx`) calls it with `forceRefresh: true`. A freshly mounted dashboard is otherwise cache-first and can render stale class data until that button is clicked.

**Logout clears all eleven.** `lib/clientCaches.ts`'s `clearAllClientCaches()` is called from `clearStoredAccessToken` (`lib/authClient.ts`), so both ways a session ends are covered — the explicit `signOut()` and `UserProvider` giving up after a failed refresh. This matters beyond staleness: `instructorStudentsStore`, `instructorActivityStore`, `acceptanceCriteriaSubmissionsStore`, `leaderboardStore`, and `previousRankStore` hold *other people's* names, answers, grades, usernames or ranks. `lib/activityStore.ts` is deliberately excluded — it is the only copy of the student's level/best score/title, so clearing it would be data loss, not cleanup.

### Database

`supabase/schema.sql` is the single migration (plain DDL, no `IF NOT EXISTS` — its footer documents the drop/rename paths for re-running). Notable: the profile table is `"user"` (a reserved word — quoted in SQL, plain `.from('user')` in supabase-js) and FKs to `auth.users`; the question-bank tables have **RLS enabled with no policies at all**, so they are unreachable except through a service-role route. Adding a table the client must not read directly should follow the same pattern. `session_log`/`answered_question_log`/`submission`/`"user"` do have own-row policies, but every data route uses the service-role client and bypasses them — the route, not the database, is what enforces scoping. `badge`, `user_badge` and `title_definition` still have no RLS (known gap, noted in the RLS block).

Indexes worth knowing before adding a query: `ix_session_log_user_id` and `ix_session_log_ended_at` (the latter matching `loadAllStudentActivity`'s two-column `ORDER BY` exactly) back the class-wide instructor reads, and `ix_user_role` backs their `role = 'student'` inner join. The partial `uq_session_log_one_active` only covers in-progress rows and can't serve a general scan.

**Timestamps are zone-less.** `started_at`, `ended_at`, `submitted_at`, `graded_at` and `updated_at` are all `timestamp` (not `timestamptz`), so PostgREST returns them without an offset and `new Date()` misreads them as local time. `lib/dateTime.ts`'s `toInstant()` pins them to UTC at the three client boundaries (`toActivityLogEntry`, `loadCompletedAttempts`, `loadInstructorACSubmissions`). Any new query handing a timestamp to the UI must route it through `toInstant` too — the real fix would be changing the column types.

Valid `activity_type` values live in `lib/activityTypes.ts` and must match `question.activity_type` in `supabase/seed.sql`. The DB enforces the set via a real lookup table, `activity_type` (GitHub #122), with `question`/`session_log`/`title_definition` FK'd against it (#123) — `lib/activityTypes.ts`'s own header comment still says this is an open point; it isn't, don't trust that comment over the schema.

### Tests

Vitest, `environment: 'node'`, glob `__tests__/**/*.test.ts`, no React/DOM tests — the mock-backed instructor UI and the localStorage stores are untested by design.

Route tests (`__tests__/api/`) mock `lib/supabase` with a `vi.hoisted` fake whose `from(table)` returns a chainable builder — `select/eq/in/order` are no-ops, and the builder is *thenable* so queries without `.single()` resolve too. Results are **queued per table** (`queue('session_log', { data, error })`) and shifted in call order, and the mock records `inserts`/`deletes`/`tables` for asserting what the route did. Route handlers are imported directly and invoked as `POST(new Request(...), { params })`.

Pure-helper tests (`__tests__/lib/`) skip `vi.mock` entirely — `requireInstructor` takes its Supabase client as an argument precisely so its test can pass in a locally built fake. Prefer that shape for new helpers.

When adding a route, copy the harness from the nearest existing test rather than inventing a new mocking style.

## Styling Guidelines

Tailwind CSS is the single, project-wide approach to styling — no CSS Modules, styled-components, or component libraries. Every page and component styles exclusively through Tailwind utility classes.

**Design tokens — the source of truth:**
- Brand colors are defined once as CSS custom properties in `app/globals.css` (`:root`, prefixed `--rc-*`), then exposed as named Tailwind colors under the `brand` key in `tailwind.config.js` (`theme.extend.colors.brand`). Use these tokens (`bg-brand-navy`, `text-brand-purple`, `border-brand-navy-border`, …) instead of writing raw hex values like `bg-[#7C4DFF]`.
- Available tokens: `brand-navy` / `brand-navy-2` / `brand-navy-border` / `brand-void` (dark surfaces), `brand-purple` / `brand-purple-dark` / `brand-purple-glow` (primary accent), `brand-teal` / `brand-teal-dark` / `brand-teal-ink` (secondary accent), `brand-gold` / `brand-gold-dark` (rewards/XP/achievements only), `brand-green` / `brand-green-dark` (success/passed states), `brand-danger` / `brand-danger-light` (errors, destructive actions), `brand-ink` / `brand-ink-muted` (text on dark surfaces).
- For the light/white content areas (inside `AppShell`'s `<main>`), use Tailwind's built-in gray scale (`text-gray-500`, `bg-gray-50`, `border-gray-100`) rather than inventing new grays.
- Border radius: use `rounded-brand-sm` (9px, small icon buttons), `rounded-brand-md` (10px, inputs/buttons/nav items), `rounded-brand-lg` (20px, cards/panels), or Tailwind's built-in `rounded-full` (pills, avatars). Don't add new arbitrary `rounded-[Npx]` values.
- Spacing: use Tailwind's default spacing scale (`p-4`, `gap-2.5`, `mb-5`, …) — no arbitrary pixel spacing.
- Typography: the font family is set once in `app/globals.css` (`body { font-family: ... }`). Don't override `font-family` in individual components.

**Rules for new pages/components:**
- No inline `style={{ ... }}` for anything expressible as a Tailwind class. Inline styles are only for genuinely dynamic, per-instance values (e.g. per-sparkle animation offsets in `components/PasswordField.tsx`).
- No new raw hex colors in `className`. If a needed color isn't in the `brand` palette yet, add it as a `--rc-*` variable in `app/globals.css` and a matching token in `tailwind.config.js` first, then use the token.
- Reuse existing shared components before writing new markup: `components/AppShell.tsx` (page shell/nav for authenticated pages; it branches its nav on `profile?.role`), `components/ActivityCard.tsx`, `components/QuestionCard.tsx`, `components/FeedbackCard.tsx`, `components/PasswordField.tsx`, `components/Avatar.tsx` (the round avatar-or-initials circle for dark surfaces — sizes are a fixed `sm`/`md`/`lg`/`xl` set, not a free className; not for `app/profile/page.tsx`'s own upload-button avatar), `components/StatTile.tsx` (one labeled stat number), and on the instructor side `components/ActivityLogTable.tsx` / `ActivityLogRow.tsx` (shared with the student activity log), `InstructorStudentCard.tsx`, `QuestionFormModal.tsx`, `CourseCard.tsx` (styled to match `InstructorStudentCard.tsx`). The student-side course browse/join card, `StudentCourseCard.tsx`, is a deliberately separate component from `CourseCard.tsx` — same visual language, different audience/data, not a shared component. Prefer extending one of these over duplicating its markup.
- Custom CSS animations that Tailwind utilities can't express (`@keyframes`, gradient-text glow, etc.) use `<style jsx>` (styled-jsx, built into Next.js) scoped to the component — see `app/dashboard/page.tsx` and `components/PasswordField.tsx`. Reference the `--rc-*` variables inside these blocks instead of hardcoding new hex values, so raw CSS and Tailwind classes never drift apart.

**Known gap:** existing pages/components still contain literal arbitrary-value classes (e.g. `bg-[#7C4DFF]`) that predate this token system. New code should use the `brand-*` tokens above; migrating existing files onto the tokens is a separate follow-up, not required for this to take effect going forward.
