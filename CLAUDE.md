# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install        # install dependencies
npm run dev        # start dev server (http://localhost:3000)
npm run build      # production build
npm test           # run all tests (vitest)
npx vitest run __tests__/api/sessions.test.ts              # run a single test file
npx vitest run __tests__/api/sessions.test.ts -t "resume"  # run tests matching a name
```

There is no lint or typecheck script; `npm run build` is the type check.

## Environment setup

Copy `.env.example` to `.env.local` and fill in your Supabase credentials. Then, in the Supabase SQL editor, run `supabase/schema.sql` followed by `supabase/seed.sql` (the question bank — without it every session start returns 400), and create two **public** Storage buckets: `avatars` for profile images, and `course-covers` (GitHub #363 follow-up) for instructor-uploaded course cover images. (README.md's mention of a `myapp_profile` table is stale — the profile table is `"user"`.)

`INSTRUCTOR_SIGNUP_CODE` (the invite code that grants the instructor role at registration, see "Auth flow" below) must be set to a real, random, per-deployment value — generate one yourself (e.g. `openssl rand -base64 24`) and set it only in each deployment's own environment (`.env.local` locally, Vercel Environment Variables in production, etc.). It must never be committed to the repo, in `.env.example` or anywhere else.

`lib/supabase.ts` accepts either `SUPABASE_URL` or `NEXT_PUBLIC_SUPABASE_URL` and exposes three factories, each returning `null` when its key is missing so routes can answer 500 instead of a confusing Supabase error:

- `getSupabaseClient()` — service-role key preferred, anon fallback. Used by every data route; it bypasses RLS, which is why those routes must derive `user_id` from the token themselves.
- `getSupabaseAuthClient()` — anon key preferred. Only `login` and `refresh`, so Supabase issues/renews a real user session.
- `getSupabaseAdminClient()` — service role, no fallback. Only `register` (`auth.admin.createUser`, which bypasses email confirmation).

Clients are created per call with `persistSession: false` — no singleton, no shared state.

## Architecture

Next.js 14 App Router, Tailwind, Supabase. The product is a requirements-practice app for students; `docs/requirements/requirements.md` is the spec, and its identifiers (`REQ-DL-3.1`, `REQ-PL-2.1`, `REQ-GAM-BL-1`, …) are cited in code comments — read the referenced requirement before changing behavior that a comment ties to one. Code comments also cite GitHub issue numbers (`GitHub #82`, `#120`, `#149`, `#169`, …) for feature-level context.

### Half-connected worlds — read this first

Parts of the app were built against real API routes, parts against localStorage mocks. The wiring-over is in progress, not finished. **Before trusting any data source, grep for who actually reads it.**

**1. Real, tested backend.** API routes + `lib/*Queries.ts` + `supabase/schema.sql` are the real implementation (sessions, answers, feedback, score, titles, activity log, instructor statistics, LLM-graded acceptance-criteria submissions), fully covered by tests. `lib/sessionClient.ts` is the UI's one gateway to the MCQ session routes — same role as `lib/authClient.ts` for auth. The student quiz flow is fully migrated: `app/activities/[slug]/page.tsx`, `app/activities/[slug]/play/page.tsx`, `app/dashboard/log/page.tsx`, and the session lists on `app/dashboard/page.tsx` / `app/courses/[id]/page.tsx` all go through `sessionClient`. (`app/activities/page.tsx` itself is no longer one of these readers — GitHub #427 turned it into "My Courses," a course-picker with no session data of its own; see the course-scoping-is-derived section below for what replaced it.) The slug↔`activity_type` mapping is declared in exactly one place: `ActivityDefinition.activityType` in `lib/activityContent.ts`.

**Points are difficulty-scaled, not flat, for both kinds (see `lib/sessionRules.ts`/`lib/llmActivityRules.ts`).** A correct MCQ answer is worth `MCQ_POINTS_BY_DIFFICULTY[level]` (Easy 10 / Medium 20 / Hard 30), written onto `question.max_score` at creation time by `lib/questionAuthoringQueries.ts`'s shared insert path rather than looked up per-answer — `scoreForAnswer` just reads whatever `max_score` the question already carries, so the all-or-nothing scoring itself is unchanged. `DEFAULT_QUESTION_MAX_SCORE` (25) is now a fallback only, for a legacy row whose `max_score` is genuinely `NULL`. The LLM-graded side mirrors this with its own scale (`LLM_POINTS_BY_DIFFICULTY`: 20/40/60) but keeps two numbers deliberately separate: `submission.llm_score` stays the raw 1-10 rating an LLM returns (so per-prompt feedback, `PROMPT_PASS_SCORE`, and the instructor statistics histogram keep reading an unscaled 1-10), while `POST .../llm/submissions` also computes `awardedScoreForRating(rating, level)` — the rating scaled proportionally onto the difficulty's point ceiling — and writes *that* to the new `submission.awarded_score` column, which `trg_submission_score` rolls into `session_log.cumulative_score` — on `UPDATE OF awarded_score`, not `INSERT` like `trg_answered_question_log_score`, since `submission` is write-before-disclose and `awarded_score` starts `NULL` until grading finishes; an `OLD.awarded_score IS NULL` guard stops a later update from double-counting. `sessionMaxScoreForDifficulty(level)` (`STORIES_PER_SESSION * llmPointsForDifficulty(level)`) replaces an old flat `SESSION_MAX_SCORE` now that the ceiling itself varies by level.

**LLM-graded activities are a second *kind*, not a fourth activity (GitHub #149/#379).** `activity_type.grading_kind` (`'mcq'` | `'llm-graded'`, `CHECK`-constrained in `supabase/schema.sql`) is what says which pool and grading path a catalog uses, and it is read for real now — by `getGradingKind` (`lib/activityTypes.ts`), which is the one place that answers "does this activity type exist *and* what kind is it" in a single round trip. `isActivityType` is deliberately left alongside it rather than reimplemented on top: every existing route test mocks its exact `.select('activity_type')` chain, and the MCQ paths have no use for the kind.

An LLM-graded activity's *session* is ordinary `session_log`, the same table and lifecycle MCQ uses: `session_to_user_story` in place of `session_to_question`, `submission.session_id` in place of `answered_question_log`, and the same abandon (`POST /api/sessions/{id}/abandon`) and completed-attempts (`GET /api/sessions/completed`) routes — nothing kind-specific was ever needed for either. `lib/llmActivityQueries.ts` mirrors `lib/sessionQueries.ts`'s role (`loadSessionStories`/`loadSessionSubmissions`/`nextUnansweredStoryPosition`, the last delegating to `nextUnansweredPosition` rather than reimplementing it, plus `loadUserStoryPool` for the level-scoped draw), and `lib/llmActivityClient.ts` mirrors `sessionClient.ts`'s.

Its routes are `POST /api/activities/{activityType}/llm/sessions`, `GET .../llm/sessions/current` and `POST .../llm/submissions` — a static `llm` segment under the existing `[activityType]`, coexisting with the static `types` sibling because static segments beat dynamic ones. The hardcoded `write-acceptance-criteria` route tree they replaced is gone; a reference to it, or to `ac_session`/`ac_session_story` (an earlier design never migrated into `schema.sql`), is stale.

**Difficulty progression applies to both kinds.** The LLM draw filters `user_story` by `difficulty_level` and starts at `findStartDifficultyLevel`'s answer, so `LevelReplaySelector`, the replay ceiling and the GitHub #371 unlock animation work identically — `user_story.difficulty_level` had existed, CHECK-constrained and indexed, read by nothing. `PROMPT_PASS_SCORE` (8, in `lib/llmActivityRules.ts`) is a per-prompt *display* threshold, compared against the raw 1-10 `llm_score`; `session_log.passed` still comes from `sessionRules`' `PASS_RATIO` against the session's own `max_score` (`sessionMaxScoreForDifficulty`, see the points paragraph above), so the two are independent by design.

**The student pages serve both kinds from one route.** `app/activities/[slug]/page.tsx` branches only where the kinds actually diverge — which read answers "is something running" — and flattens the two differently-shaped results into one `CurrentProgress` at the fetch; everything downstream is kind-agnostic because both flows write identical `session_log` rows. `.../play/page.tsx` resolves the slug once and hands off to `components/LlmPlayView.tsx` or its own `QuizPlayView`; the branch sits *above* both because hooks can't be conditional and mounting the MCQ view for an LLM activity — even for one render — would fire `loadCurrentSession` against the wrong session model. The `write-acceptance-criteria` entry in `ACTIVITIES` (`lib/activityContent.ts`) is kept deliberately even though its static pages are gone: `useResolvedActivity` checks that array first, so it is what keeps the old URL resolving, at zero network cost, with real metadata instead of generic fallbacks.

**Grading is per-prompt-author.** `POST .../llm/submissions` resolves the provider from `user_story.creator_id` → `instructor_llm_config` (most recent row; `is_active` is not consulted), so the seeded prompts — `creator_id IS NULL` — are ungradable by design and 500 with "the instructor who created this prompt has not configured an LLM provider". Any QA run has to author a prompt through the UI; testing against the seeded set looks like a failure that isn't one.

**2. The leveling mock.** `lib/activityStore.ts` is still a localStorage mock (`rc_activity_progress_v1`) of the leveling/history side of the domain — current difficulty level, best score, earned title. **Nothing writes to it any more**: `startSession`/`abandonSession`/`answerQuestion`/`currentQuestionId`/`getBestScore` have no callers at all since the play flow moved to the API, so every value it can return is frozen at its default — `level` is always `1`, `getTitle` always `'Not yet started'`, `getHighestTitleOverall()` always `null`, `state.inProgress` always `null`. Treat anything it returns as a lie, not as stale data.

It is now read by only two places, and both are showing those frozen values: `app/dashboard/page.tsx` (`getActivityState`, whose "Continue where you left off" panel is therefore permanently empty even with a real session running) and `components/AppShell.tsx` (`getHighestTitleOverall`, falling back to `'Getting started'`). `app/activities/page.tsx` was the third and no longer touches it — GitHub #272 was exactly this bug surfacing as misleading card text; the card-title/level logic that fixed it now lives in `app/courses/[id]/page.tsx` (`app/activities/page.tsx` was rebuilt into "My Courses" by GitHub #427 and no longer renders activity cards at all — see below), reading `loadStudentTitles` for the title and the in-progress `SessionListEntry` for the level. `app/activities/[slug]/page.tsx` never touched it either: "is something running?" there comes only from `loadCurrentSession`. Migrating the last two readers the same way is what's left; note `activityStore.ts:128` also uses a `0.8` pass threshold against `sessionRules`' `PASS_RATIO = 0.75`.

Card status text has one source: `lib/activityCardStatus.ts` (`deriveActivityCardStatus` + `activityCardStatusLabel`). Its two-slot rule is load-bearing — the mastery **title** slot renders only a genuinely earned title (`StudentTitle.difficultyLevel !== null`, never string-matched against the server's `'Not yet started'`), and the **status** line says what the next click does. Putting a placeholder back into the title slot re-creates #272. `deriveActivityCardStatus` has four states, ranked by precedence: a running session (`'in-progress'`) always wins since that's what the next click resumes; then `'mastered'` (every difficulty level passed — `highestPassedLevel === MAX_DIFFICULTY_LEVEL`), which outranks a plain `'best-score'` as strictly more complete information about the same history; then `'not-attempted'`.

`lib/masteryTitles.ts`'s `buildMasteryTitleEntries` (GitHub #39) reconciles `GET /api/students/{id}/titles` for a *different* screen — the profile page's full mastery grid (`components/MasteryProgressSection.tsx`), the dashboard's own mastery grid (`app/dashboard/page.tsx`), and `app/students/[id]/page.tsx` for a peer's public profile — with the **opposite** display rule from `activityCardStatus.ts` above: `/titles` only returns an entry for an activity type the student has actually attempted, but these grids are supposed to show every activity the student *could* attempt, so untried ones are deliberately filled in as `currentLevel: null` / "not yet started" placeholders — the exact placeholder the card-status two-slot rule exists to avoid, just on a screen where showing a to-do state is the point instead of the bug.

`buildMasteryTitleEntries`'s "every activity the student could attempt" side used to be the static `ACTIVITIES` array (`lib/activityContent.ts`), including each entry's hardcoded `titles: Record<Difficulty, string>` ladder — fixed at compile time, covering only the three built-in activity types, and out of sync with `title_definition`'s actual `title_name` values (e.g. `'Story Master'` in `activityContent.ts` vs `'Story Expert'` in the seeded table). It's now `GET /api/students/{studentId}/available-titles` (self-only, same rule as `/score`/`/titles` on this path): `lib/titleQueries.ts`'s `loadAvailableTitleLadders` calls `listActivityTypesForCourses` (the same course-scoped listing `GET /api/activities` uses) for whichever course-id list the caller passes in, then reads `title_definition` filtered to just those activity types, returning every level 1..`MAX_DIFFICULTY_LEVEL`'s title (`null` if no row exists yet) per activity — real data, and, being course-scoped, it also surfaces an instructor-created custom quiz's ladder, which the old `ACTIVITIES`-only grid never could. `GET /api/students/{id}/public-profile` embeds the same `availableTitles` shape for a peer's profile, computed from `targetCourseIds` it already fetched for its shared-course check rather than a second `getEnrolledCourseIds` read — a peer can't call the self-only route for someone else's ladder, so this is the only path that serves it for `app/students/[id]/page.tsx`'s non-self branch. `buildMasteryTitleEntries` takes this list plus the `/titles` response and falls back to a generic `Level N` label for any rung with no `title_definition` row, the same placeholder `buildCustomActivityDefinition` used to hardcode. `ActivityDefinition.titles` still exists on `ACTIVITIES`/`buildCustomActivityDefinition` only because `lib/activityStore.ts` — the frozen leveling mock two paragraphs up — still reads it; it has no other live reader.

**Courses — real, but a separate, parallel structure (REQ-DL-5, GitHub #241/#242).** `course` and `student_course` tables (`supabase/schema.sql`), `lib/courseQueries.ts`, and two real clients — `lib/courseClient.ts` (instructor) and `lib/studentCourseClient.ts` (student) — back a full create/browse/join/roster flow: `app/instructor/courses/page.tsx` (list + `CreateCourseModal`, a button-triggered popup — GitHub #241 follow-up, replacing the page's old permanently visible inline form) and `app/instructor/courses/[id]/page.tsx` (roster, rename, enroll/unenroll, join-code display; its roster search + a "Needs attention"/"No attempts yet"/score-sort filter dropdown is `components/CourseStudentsDrawer.tsx` and `components/StudentFilterControls.tsx` over `lib/courseStudentFilters.ts`'s pure `filterAndSortCourseStudents` — one function so the drawer and the full roster page can't disagree about what a filter means, each option reading a field `GET /api/instructor/courses/{id}` already returns per student rather than a new aggregation) on the instructor side; `app/courses/page.tsx` (`StudentCourseCard`, browse-by-name/professor + join-by-code) on the student side — `components/StudentCourseCard.tsx`'s own comment notes its Leave action (GitHub #324) moved here from `app/profile/page.tsx`'s `MyCoursesSection`, which no longer exists. A course has a nullable, unique `course_code` — `lib/courseQueries.ts`'s `findOwnedCourse` is a reusable 404-then-403 ownership check other instructor routes don't have. The join code itself is never sent to a browsing student (`JoinableCourse` in `lib/courseTypes.ts` has no `code` field) — only `POST /api/courses/join` resolves it, server-side. **Course scoping is real for activities now (see the course-scoping-is-derived paragraph below) but still missing from two of the three class-wide instructor reads**: `GET /api/instructor/statistics` and `/sessions` (and the instructor dashboard/roster pages that call them) are still class-wide with no `courseId` filter — the "no professor-to-quiz/-student ownership in the schema" gap those routes' own comments describe is now only half true (the schema has `course`; these routes just don't consume it). `GET /api/instructor/activities` is the exception: GitHub #171 already scopes it to catalogs `creator_id = guard.user_id` owns (still every student on those catalogs, not course-scoped) — see the Reading Sessions section below. The one cross-link that exists: `components/AddStudentForm.tsx` reuses `loadInstructorStudents` (the whole-class roster) as its enrollment search, not a course-scoped query. Ignore in-code comments in `lib/courseQueries.ts` and `app/api/courses/join/route.ts` that mention a `lib/mockCourses.ts` still backing `StudentCourseCard` — that file doesn't exist; the component already calls the real `studentCourseClient`. Per-course enrollment is a real round trip too: `courseClient.ts`'s `addStudentToCourse`/`removeStudentFromCourse` back `POST`/`DELETE /api/instructor/courses/{id}/students[/…]`, and `exportCourseReport` backs `GET /api/instructor/courses/{id}/export` (REQ-PL-3.4.3) — a depersonalized CSV (`lib/csv.ts`'s `toCsv`, no student name column) of every `session_log` attempt by that course's roster, reusing `loadStudentActivityForIds` rather than a new query. Unenrollment has two routes, not one: the instructor-driven `DELETE /api/instructor/courses/{id}/students/{studentId}` above, and a self-service `DELETE /api/courses/{courseId}/enrollment` (GitHub #325) a student calls on themselves, scoped to their own token — deliberately not idempotent like the instructor route, since it names a specific caller-owned resource and 404s on an unknown course or a caller who was never enrolled. Instructors can also delete the whole course — `DELETE /api/instructor/courses/{id}` (GitHub #326/#327) reuses the same `authorizeCourse`/`findOwnedCourse` 404-then-403 dance `GET`/`PATCH` on that route already share, counts the roster before deleting, and returns `{ courseId, unenrolledCount }`. `fk_student_course_course` is `ON DELETE CASCADE`, so enrollments disappear in the same transaction; nothing else references `course_id` (`session_log` and `question` don't have one), so scores, titles and activity history survive a course's deletion — only the course, its join code, and its CSV export are gone. `components/DeleteCourseModal.tsx` states that distinction before the instructor confirms, and defaults focus to Cancel.

**The leaderboard — real now.** `GET /api/courses/{courseId}/leaderboard` (`lib/leaderboardQueries.ts`'s `computeCourseLeaderboard`) ranks every student in `student_course` — not just those who've attempted something, the opposite of `loadAllStudentActivity`'s known "roster derived from attempts" gap — by the exact same `sumBestScores` reducer `computeStudentScore` (`lib/scoreQueries.ts`) uses for the sidebar score pill, so the two numbers can't drift. Only `username`/`avatar_url` leave `"user"`, via an `!inner` join filtered to `role = 'student'` (backed by `ix_user_role`, the same pattern `loadAllStudentActivity`'s `STUDENT_EMBED` uses) — no name/age/semester. Standard competition ranking (ties share a rank, the next rank skips) with username as the deterministic tiebreaker. Authorization is enrollment, not ownership or role: the route 404s an unknown `courseId` before checking anything else, then 403s a caller who isn't themselves in `student_course` for it — the one genuinely new cross-user authorization rule in the app, since the only other student-callable cross-user read, `GET /api/courses` (`listJoinableCourses`), discloses course metadata but never another student's identity or score.

`app/leaderboard/page.tsx` and the dashboard's `components/LeaderboardPreview.tsx` both read this route through `lib/studentCourseClient.ts`'s `loadCourseLeaderboard` — cached in `lib/leaderboardStore.ts` (courseId-keyed, same shape as the other client caches) so the two share one cache entry per course. `rankChange` is still never part of the server response (`lib/leaderboardTypes.ts`'s own doc on `LeaderboardEntry`) — `loadCourseLeaderboard` attaches it from `lib/previousRankStore.ts`'s last-recorded per-course rank snapshot (`getPreviousRanks`/`withRankChange`), and each page records the new snapshot itself, in a `useEffect` keyed on the fetched entries so the write happens strictly *after* that render used the *old* snapshot — writing first would make a delta compare a fetch against itself. That store's own header names the honest limits (per device, per browser, wiped on logout) and a zero-migration alternative for later (replay `sumBestScores` over `session_log` filtered to `ended_at < T`, no new table needed). The leaderboard cache has no automatic invalidation when *another* student's score changes it — same staleness `loadInstructorActivities` documents — so `app/leaderboard/page.tsx` has a manual Refresh button, and the play page's `handleFinishSummary` blanket-clears the whole leaderboard cache (not a single courseId — the page doesn't know which of the student's courses to target) whenever the student's *own* score changes on session completion. Course lists for both the switcher and the preview come from `loadMyLeaderboardCourses` (`lib/studentCourseClient.ts`, GitHub #328) — the `alreadyMember`-filtered slice of `loadJoinableCourses`, cached session-scoped in its own store (`lib/leaderboardCoursesStore.ts`) so revisiting either view within the same tab session doesn't re-fetch the course list; `loadJoinableCourses` itself stays uncached, since `app/courses/page.tsx`/`MyCoursesSection` need a just-joined course to appear without waiting out a stale session cache. `lib/leaderboardStore.ts` and `lib/leaderboardCoursesStore.ts` are deliberately `sessionStorage`, not `localStorage` (GitHub #329) — unlike every other client cache in this app, a stale leaderboard entry must not survive an app restart, so a fresh tab always gets exactly one real fetch regardless of what a previous session left cached. `app/leaderboard/page.tsx`'s Refresh button forces both caches (course list and entries) together, since course membership can itself have changed mid-session.

**A classmate's public profile — real now too.** `GET /api/students/{studentId}/public-profile` (`app/students/[id]/page.tsx`, reached from a leaderboard/preview username) is real, and `lib/mockLeaderboard.ts` — the last of the leaderboard feature's Phase-1 mocks — is deleted. This route deliberately does **not** reuse the `/api/students/{studentId}/*` preamble every other route under that path shares (`score`, `titles`, `activities`, `history`): those all 403 the instant `studentId` isn't the caller's own id, by design, which is exactly wrong here — the route exists to serve someone *else's* data. Its authorization is instead "do the caller and the target share a course" (`student_course` intersection), built on `isEnrolledInAnyCourse` (`lib/courseQueries.ts`) — the same shared helper `GET /api/courses/{courseId}/leaderboard`'s own enrollment check now uses too (there with a single-course list, here with the target's full course list via `getEnrolledCourseIds`), so "enrolled" can't drift between the two routes. 404-then-403 ordering: unknown `studentId` → 404; a non-student target (an instructor has no public profile) → 403; no shared course → 403. The response is exactly `{ username, avatarUrl, biography, score, titles }` — `score`/`titles` are `computeStudentScore`/`computeStudentTitles`'s own numbers, not re-derived, and `role` is selected server-side only to decide the 403, never returned. `app/students/[id]/page.tsx` reads this through `lib/sessionClient.ts`'s `loadPublicStudentProfile` (uncached, same reasoning as `loadStudentTitles`) for the peer branch; the `isSelf` branch is unchanged, still reading `loadStudentScore`/`loadStudentTitles` directly. Shared display components across the leaderboard screens: `components/LeaderboardTable.tsx`, `LeaderboardCourseSwitcher.tsx`, `LeaderboardSkeleton.tsx`, `LeaderboardRankBadge.tsx`, `RankChangeIndicator.tsx`, `Pagination.tsx`, and `components/Avatar.tsx` (extracted from `AppShell.tsx`/`StudentDetailHeader.tsx` duplication; a fixed `size` set, not a free className, so call sites can't drift into slightly different circles — deliberately *not* used by `app/profile/page.tsx`, whose avatar is an upload-button, not a display avatar).

Most of the front-end-first instructor work that used to sit in a third "UI-only mock arrays" world is gone: `lib/mockQuestions.ts` (`MOCK_QUESTIONS`) was replaced by the question-bank routes (GitHub #170/#121/#158). (`lib/mockStudentActivity.ts` was another one and is gone too — the instructor dashboard and roster now read `GET /api/instructor/activities`.)

**Question Catalogs — "Quizzes" (GitHub #347/#348) and "Question Catalogs" (GitHub #359) are the same feature, not two.** A "catalog" is exactly what this codebase already calls a "quiz": a named, ownable row in the `activity_type` lookup table (`quiz_name`, `description`, `creator_id`, GitHub #347), with every `question` whose `activity_type` column points at it. `POST /api/activities/types` creates one (`lib/quizClient.ts`'s `createQuiz`). **As of the most recent change, catalogs are no longer globally shared browsing** — `GET /api/instructor/quizzes` (`lib/activityTypeQueries.ts`'s `listQuizzesWithAuthorAndCount`, now taking an `instructorId` and filtering `.eq('creator_id', instructorId)`) lists only catalogs the caller created; built-in catalogs (`creator_id IS NULL`) and colleagues' catalogs never appear, the same "mine only" convention the Courses pages use. `app/instructor/quizzes/page.tsx` dropped its author filter dropdown and Author column accordingly (there's only ever one author: the caller) — treat any surviving mention of "catalogs are shared" as stale. Clicking a catalog on that page opens `app/instructor/quizzes/[activityType]/page.tsx` — read-only by default (`GET /api/instructor/quizzes/{activityType}`, `lib/activityTypeQueries.ts`'s `getQuizByActivityType` + `listCatalogQuestions`), an "Edit" toggle away from add/edit/delete on the caller's own questions (`POST`/`PATCH`/`DELETE /api/instructor/questions[/…]`; `DELETE` is new in GitHub #359). A question already used in a student session (a `session_to_question` row exists) still 409s on a plain `DELETE` — `question_to_answer`/`answered_question_log`/`session_to_question`'s FKs to `question`/`answer` have no `ON DELETE` clause — but the 409 body now carries an `impact` payload (`sessionsCount`/`answeredSessionsCount`/`studentsAffectedCount`/`pointsAtRisk`) rather than being a dead end: `DELETE .../questions/{id}?force=true` deletes it anyway, and for every affected session reduces `cumulative_score` by whatever this question contributed there and `max_score` by the question's own `max_score`, recomputing `passed` for sessions already `completed` — so a deleted question's points actually leave the student's score (`computeStudentScore` only ever reads `session_log.cumulative_score`), not just the row. `daily_challenge_attempt` rows referencing the question are cleaned up unconditionally alongside it, since that table has the same FK gap but isn't part of the session-score story. `components/DeleteQuestionModal.tsx` is the two-step confirmation this drives: a first "Delete question" attempt that, on 409, swaps in the `impact` warning and a "Delete anyway" button that retries with `force`. That detail route now 403s (no body) when `creatorId !== guard.user_id` — same 404-then-403 ordering as `lib/courseQueries.ts`'s `findOwnedCourse` — and the page renders "You don't have access to this catalog." for it, distinct from its 404 "This catalog doesn't exist." `getQuizByActivityType` itself stays deliberately unscoped by creator and returns `creatorId` as a sibling field (not folded into `QuizMeta`): it's shared by three callers with three different authorization rules — this route (enforces "mine only" itself), the assembled-quiz "catalog in the context of this quiz" view (authorized via quiz ownership, so a linked built-in or colleague's catalog must stay viewable there), and the student-facing single-activity route (authorized via course enrollment). `QuestionFormModal`'s quiz picker used to be a hardcoded two-item list (only the original two Type A activity types) — GitHub #359 replaced it with a `quizOptions` prop, since a hardcoded list could never target a custom catalog; the catalog detail page passes its own single catalog, effectively locking the field. A question has exactly one `activity_type` column, not a join table, so a catalog's edit mode can never leak into another catalog — that isolation falls out of the schema, not route-level enforcement. GitHub #379 made that page branch on `grading_kind`: an `llm-graded` catalog shows prompts (`listCatalogUserStories`, `components/CatalogPromptCard.tsx`, `PromptFormModal`, `ConfirmModal` for delete, plus a per-level coverage banner against `STORIES_PER_SESSION`) backed by `POST`/`PATCH`/`DELETE /api/instructor/user-stories[/…]`, whose shared body validation lives in `lib/userStoryInput.ts` because a `route.ts` may only export HTTP handlers. `GET /api/instructor/quizzes/{activityType}` returns **both** pools with one always empty rather than a discriminated union, and only queries the one the kind calls for. The existing question markup was left inline and untouched next to the new branch, deliberately — the cheapest guarantee that the MCQ path couldn't regress. Creating a catalog now *requires* a `gradingKind` (`CreateCatalogModal`'s two radio cards start unselected, and `POST /api/activities/types` 400s without one) since the kind can never be edited afterwards. The narrower, still-unused `GET /api/instructor/quizzes/:activityType/:difficultyLevel/questions` (below) is a different, pre-existing route this didn't touch. The genuinely different "assemble a quiz from one or more catalogs, scoped to a course" feature this paragraph used to flag as undesigned is now built — as its own entity, not a third meaning bolted onto `activity_type` — see the next paragraph.

**Assembled quizzes (GitHub #360) are a third, deliberately separate "quiz" concept — not a rename, not a merge.** Where a catalog (`activity_type`) *is* a flat, leveled pool of questions, an `assembled_quiz` (`supabase/schema.sql`) *composes* one or more catalogs for exactly one course: `assembled_quiz(assembled_quiz_id, quiz_name, description, course_id, creator_id, created_at)` plus the m:n join `assembled_quiz_catalog(assembled_quiz_id, activity_type)`, both new tables, RLS-enabled with no policies like `question`/`course`. `course_id` is `NOT NULL` with `ON DELETE CASCADE` — an assembled quiz composed for a course has no meaning once that course is gone, same reasoning as `student_course`'s cascade. This was a deliberate decision, not the only option: `activity_type` already *could* have grown a `course_id` and a catalog-reference table, but doing so would have broken the "one `activity_type` = one flat leveled pool" invariant every other piece of the app relies on (`session_log.activity_type`, `title_definition`, `question.activity_type` all key on that atomicity) — see the previous paragraph's "own name" note, written in anticipation of exactly this issue. `lib/assembledQuizQueries.ts` holds the query layer: `createAssembledQuiz` (insert quiz + link rows, deleting the quiz row on a link-insert failure — no transaction, same rollback-by-hand pattern `POST /api/instructor/questions` uses), `listAssembledQuizzesForInstructor` (scoped to `creator_id`, *not* shared the way catalogs are — a quiz is built for one of the caller's own courses, and courses aren't shared between instructors either), and the random-draw pair `loadCatalogQuestionPool`/`pickRandomQuestions`. The draw is dynamic, not materialized at creation time: no per-level question set is stored anywhere, so editing a linked catalog's questions later is reflected immediately, the same "always current" property the catalog detail page (GitHub #359) already has. **`loadCatalogQuestionPool`/`pickRandomQuestions` themselves are still only called by the instructor composition preview, never by a live student session** — there is still no "take the whole assembled quiz as one unit" route; a student always plays one catalog (`activity_type`) at a time, same as before assembled quizzes existed. What a later change *did* wire up live, for both kinds: `POST /api/sessions`'s own draw (not these functions) filters out a catalog's `quiz_excluded_question` rows for the specific assembled quiz that granted access, via `getAccessibleCourseForActivity`'s `assembledQuizId` plus `listQuizExcludedQuestionIds`; `POST /api/activities/{activityType}/llm/sessions` does the identical thing on the `user_story` side, via `listQuizExcludedUserStoryIds` — see the Session model section below. Hand-picked extras (`assembled_quiz_extra_question`/`assembled_quiz_extra_user_story`) are still not consulted by either live draw — only exclusions are enforced today, not hand-picks. Create/browse (`POST`/`GET /api/instructor/assembled-quizzes`) and the instructor UI at `app/instructor/assembled-quizzes/page.tsx` (`lib/assembledQuizClient.ts`) are reachable from their own "Quizzes" nav item — deliberately a *different* sidebar entry from "Question Catalogs" (`instructor-quizzes`), sitting right after it, so the two "quiz" concepts this section distinguishes stay visually distinct too. Both `page.tsx` create flows (this one and `instructor-quizzes`' catalog list) are button-triggered popups (`CreateQuizModal`/`CreateCatalogModal`), not permanently visible inline forms — same for course creation (`CreateCourseModal`, `app/instructor/courses/page.tsx`); all three, plus `ConfirmModal` (below), share `components/useModalDismiss.ts` for the focus-trap/Escape/backdrop-click/focus-return wiring rather than each hand-rolling it independently the way the older modals (`QuestionFormModal`, `EditCourseModal`, `DeleteCourseModal`, `DeleteQuestionModal`) still do — those weren't retrofitted, so both patterns coexist; copy whichever a new modal is structurally closer to.

**Managing an assembled quiz's composition (GitHub #361) — "displayed as copies of the originals" is an exclusion list, not duplicated rows.** A quiz still references its ORIGINAL catalogs via `assembled_quiz_catalog`; `quiz_excluded_question(assembled_quiz_id, question_id)` (`supabase/schema.sql`, both FKs `ON DELETE CASCADE` — unlike `question_to_answer`/`answered_question_log`'s lack of one, there's no student history here to protect) is the only new table, and it is the *entire* mechanism: excluding a question for one quiz writes exactly one row there and touches `question`/`answer` never, which is what makes the original catalog provably unaffected — by construction, not by convention. The alternative (cloning question/answer rows per quiz) was rejected because it would need its own sync story the moment the original catalog changes; the exclusion list needs none, since `lib/assembledQuizQueries.ts`'s `getQuizComposition`/`loadCatalogQuestionPool` always compute "what's active" by re-reading the catalogs' current questions minus the current exclusion set, live, on every call. Routes live under `/api/instructor/assembled-quizzes/{quizId}/…`, not `/api/instructor/quizzes/{quizId}/…` — GitHub #359's catalog detail route already owns `/api/instructor/quizzes/[activityType]`, and Next.js rejects two differently-named dynamic segments (`[activityType]` vs `[quizId]`) at the same route position, so this nesting is required, not stylistic. `findOwnedAssembledQuiz` (`lib/assembledQuizQueries.ts`) is `lib/courseQueries.ts`'s `findOwnedCourse` pattern reused for quizzes — every composition route's ownership check goes through it. `GET /api/instructor/assembled-quizzes/{quizId}` (`app/instructor/assembled-quizzes/[quizId]/page.tsx`) returns the quiz's linked catalogs with a *genuinely* active count (total minus this quiz's own exclusions, never another quiz's or the catalog's own) plus per-level coverage against `QUESTIONS_PER_SESSION` — the page turns any level below that into a visible warning banner *before* a student hits it, on top of `POST /api/sessions`' own live enforcement of the same minimum against the exclusion-filtered pool (see the previous paragraph). Excluding/including one question happens on `app/instructor/assembled-quizzes/[quizId]/catalogs/[activityType]/page.tsx` — the catalog "as it applies to this quiz", read-only over the question content itself (no edit/delete affordance renders there at all; that only exists on the real catalog, GitHub #359) with excluded rows grayed out and badged rather than hidden, so re-including one is a single click away. Deleting a quiz (`DELETE /api/instructor/assembled-quizzes/{quizId}`) is a plain hard delete, not a soft one: no session ever references an `assembled_quiz` (`session_log` only ever points at a catalog's `activity_type`, and has no `assembled_quiz_id` column), so even now that students actually take sessions through a quiz's catalogs, deleting the quiz destroys no attempt history — only the access grant and this quiz's own exclusions/extras — `assembled_quiz_catalog` and `quiz_excluded_question` cascade with it. `ConfirmModal` (`components/ConfirmModal.tsx`) backs both this delete and "remove a catalog from a quiz" — the first shared (not just copied) confirmation dialog in the app, justified once a second near-identical one was needed at the same time; `DeleteCourseModal`/`DeleteQuestionModal` predate it and weren't migrated.

**Hand-picking individual questions onto a quiz (GitHub #380) is the inverse of the exclusion list above, not a variant of it.** `assembled_quiz_extra_question(assembled_quiz_id, question_id)` — both FKs `ON DELETE CASCADE`, same reasoning as `quiz_excluded_question`'s — adds a question directly to a quiz independent of whether its catalog is linked via `assembled_quiz_catalog` at all; unlike exclusion, there's no membership requirement to satisfy first. `lib/assembledQuizQueries.ts`'s `getQuizComposition`/`loadCatalogQuestionPool` union it in: the draw pool is "every active question from every linked catalog, minus this quiz's exclusions, plus this quiz's hand-picked extras" — `getExtraQuestionIds`/`addExtraQuestionToQuiz`/`removeExtraQuestionFromQuiz` are the CRUD trio, each idempotent per-question so a batch pick doesn't abort on one already-picked id (`23505`). Two routes back it: `POST`/`DELETE /api/instructor/assembled-quizzes/{quizId}/extra-questions[/…]` picks/unpicks an *existing* question (which does not need to belong to any of the quiz's linked catalogs — that's the entire point), and `POST /api/instructor/assembled-quizzes/{quizId}/questions` creates a brand-new question and hand-picks it in one atomic request, rolling back the just-created question (`deleteQuestionWithAnswers`) if the hand-pick insert fails afterward — the same rollback-by-hand discipline `createAssembledQuiz` and `POST /api/instructor/questions` already follow. `app/instructor/assembled-quizzes/[quizId]/page.tsx` renders these alongside the linked catalogs' active questions.

**Course-scoping for activities is derived, not stored — `activity_type_course`, an earlier direct catalog-to-course join table, was removed.** It briefly existed as a fourth meaning of "course-scoped" (one join row per catalog, `uq_activity_type_course_activity_type` capping it at one course each), but it contradicted the moment two courses wanted to reuse the same catalog through two different assembled quizzes: a catalog is meant to be a standalone, reusable, author-owned resource (the Question Catalogs paragraph above), not tied to one course. `supabase/schema.sql`'s migration notes document the `DROP TABLE IF EXISTS activity_type_course` an existing deployment needs to run by hand; a stale comment anywhere still describing that table as live should be treated as leftover, not current behavior. Course-scoping is now entirely derived through the quiz-composition tables above: Course → `assembled_quiz` → `assembled_quiz_catalog` → catalog. `lib/activityCourseQueries.ts`'s `getAccessibleCourseForActivity` is the one place that answers "which of the caller's enrolled courses grants access to this activity_type" — it resolves the caller's `getEnrolledCourseIds`, then looks for an `assembled_quiz_catalog` row whose `assembled_quiz.course_id` is one of them (an `!inner` embed — a non-inner embed would null the field instead of dropping the row). `checkActivityAccess` wraps that into the same `'ok'`/`'forbidden'` outcome it always returned, and is still what `GET /api/activities/{activityType}/questions` and the LLM-graded session route use. `POST /api/sessions` no longer goes through that wrapper, though: since the session draw needs `assembledQuizId` to filter the granting quiz's exclusions (see the Session model section), it calls `getAccessibleCourseForActivity` directly and checks for a `null` link itself, rather than the narrower yes/no `checkActivityAccess` gives. It still folds "no quiz composes this catalog at all" and "some quiz does, but not in a course the caller is enrolled in" into the same `'forbidden'` outcome — from the caller's point of view both just mean "not available to you," and distinguishing them would leak which catalogs/quizzes exist otherwise. A catalog can now grant access through more than one course at once (via separate assembled quizzes), which a single owning-course link table could never express.

`POST /api/activities/types` no longer takes or requires a `courseId` — a catalog is created owned only by `creator_id`, and becomes visible to students only once an instructor composes an `assembled_quiz` that references it (see above). `GET /api/instructor/quizzes` and `GET /api/instructor/quizzes/{activityType}` (`lib/activityTypeQueries.ts`) dropped the course embed this paragraph used to describe; the list route embeds `quizCount` instead (`assembled_quiz_catalog(count)` — how many assembled quizzes currently compose this catalog), which replaced a Course column with a quiz-usage count on `app/instructor/quizzes/page.tsx`. `CreateCatalogModal.tsx` has no course `<select>` for the same reason — its own header comment notes the field used to be required back when `activity_type_course` existed.

On the student side, `checkActivityAccess` gates `POST /api/sessions` (session start/resume) and `GET /api/activities/{activityType}/questions` — the two dead-and-live places that used to only check `isActivityType`'s existence, not visibility. Two new routes answer the "what can I see" question those gates otherwise have no way to disclose: `GET /api/activities` (`lib/activityCourseQueries.ts`'s `listActivityTypesForCourses`, fed by `getEnrolledCourseIds`) lists every activity linked to any course the caller is enrolled in, and `GET /api/activities/{activityType}` (single-row) is what `lib/useResolvedActivity.ts` falls back to when a slug isn't one of the three built-ins `lib/activityContent.ts` knows statically — the hook that now backs both `app/activities/[slug]/page.tsx` and its play page, checking the static `ACTIVITIES` array first (zero network cost, unchanged behavior for the built-ins) and only hitting the server for a genuinely unrecognized slug, surfacing `'not-found'` vs `'forbidden'` separately so the page can say which. `lib/activityContent.ts`'s `buildCustomActivityDefinition` turns that route's response into an `ActivityDefinition`-shaped object (generic instructions, `category: 'Custom'`, placeholder `titles` ladder) so the existing MCQ play flow — already fully server-driven for prompts/options/scoring, per the dead-code note below — needs no changes to run a course-scoped custom catalog; only display metadata was ever missing. `ActivitySlug` is now `string` (same "kept as an alias so `: ActivitySlug` annotations keep compiling" move `ActivityType` made in GitHub #347) since a slug can be a raw `activity_type` key now, not just one of the three built-ins.

**`app/activities/page.tsx` is no longer the student's activity list — GitHub #427 replaced it with "My Courses," a flat cross-course activity list is gone entirely.** The route and `AppShell`'s `'activities'` nav slot are unchanged, but the page now just lists the courses the student has joined (`GET /api/courses/mine` via `lib/studentCourseClient.ts`'s `loadMyCourses`, rendered as `components/JoinedCourseCard.tsx` cards) — it answers "which courses am I in," not "what do I need to do." `GET /api/courses/mine` (`lib/courseQueries.ts`'s `listEnrolledCoursesForStudent`) is deliberately a separate route from `GET /api/courses` (`listJoinableCourses`, browse/join-by-code): the browse route excludes courses with no join code, which would hide a course an instructor enrolled the student in directly, so "every course I can join" and "every course I'm actually in" need different queries.

Clicking a course opens `app/courses/[id]/page.tsx`, which owns the course-scoped activity-card behavior the old `app/activities/page.tsx` used to have: it calls `GET /api/activities?courseId=` (via the new `lib/activityDiscoveryClient.ts`'s `loadAvailableActivities`, not `sessionClient`) and resolves each returned entry through `getActivityByType` (rich static metadata) or `buildCustomActivityDefinition` (generic fallback), same as before — just scoped to one course's activities instead of every course the student is in. The `?courseId=` param on `GET /api/activities` (`app/api/activities/route.ts`) reuses the same `listActivityTypesForCourses` query, narrowed to a single course id that must already be in the caller's own `getEnrolledCourseIds` result — an unrecognized or foreign course id 403s (no body), the same "don't disclose what exists" reasoning `checkActivityAccess`'s `'forbidden'` outcome documents. This is also why the three built-ins can still show as "not available": they're reachable only once an instructor composes an `assembled_quiz` that references them for some course, same as any freshly created custom catalog. `components/StudentCourseCard.tsx` on the browse/join page (`app/courses/page.tsx`) links an already-joined card into this same `app/courses/[id]/page.tsx` destination too (GitHub #427 follow-up) — the cover+name+meta area becomes a `Link`, with the Leave button kept as a sibling (not nested inside it, since a `<button>` inside an `<a>` is invalid HTML) so Leave doesn't also navigate; a not-yet-joined card stays non-clickable.

One instance of that third world is still very much alive, though: `app/instructor/students/[id]/page.tsx` (the per-student detail page, GitHub #127) reads `lib/mockStudentAttempts.ts`'s `getMockStudentAttempts()` — a fixed, fabricated attempt history — regardless of which student was actually clicked; the `studentId` param and the `MOCK_CLASS_AVERAGE` constant on that page aren't wired to anything real yet. `components/StudentScoreChart.tsx`, `StudentActivityBreakdown.tsx`, and `lib/studentAttemptMetrics.ts` all consume this same mock shape (`StudentAttemptDetail`). `lib/mockStudentAttempts.ts`'s own header comment describes the shape a real per-student endpoint would need to return so those consumers keep working unchanged.

But `resolveCourseScope`/`requireCourseScope` are no longer the only thing this file does: `GET /api/instructor/students` scopes its default (non-`?scope=all`) response through a second, aggregate function in the same file, `resolveInstructorStudentIds` — "every student across *all* courses I own," automatically, with no `?courseId=` picker needed — built alongside the single-course pair rather than on top of it, since "pick one course" and "show me everything I have" are genuinely different questions the existing functions don't answer. `lib/courseQueries.ts` gained the two bare-id helpers this composes: `listOwnedCourseIds` (every course a `creator_id` owns) and `loadEnrolledStudentIdsForCourses` (every distinct student across a given set of courses, deduped). `?scope=all` opts back into the original unscoped query — the one legitimate remaining caller of the full roster is `components/AddStudentModal.tsx`'s enrollment search, which must be able to find a student who isn't in any of the instructor's courses yet.
- `question.user_id` (GitHub #201) records which instructor authored a question, and `GET /api/instructor/questions` (GitHub #170) now scopes to it (`.eq('user_id', guard.user_id)`), the same way `GET /api/instructor/user-stories` (GitHub #225) scopes by `user_story.creator_id`. Both columns are nullable, and neither `supabase/seed.sql`'s `question` nor (as far as the app can create one) any `user_story` row is ever inserted with an owner — so a fresh instructor's Question Bank page is genuinely empty until they've added questions of their own via the existing `POST /api/instructor/questions`. That's intended: unowned/seeded rows aren't "theirs" to show.

### Auth flow

`lib/authClient.ts` is the only place the UI talks to auth routes. It stores both the Supabase `access_token` and `refresh_token` in localStorage (register additionally signs in, since the admin API returns a user but no session). `components/UserProvider.tsx`'s `useUser()` is the single source of truth for the token, the signed-in profile, and (GitHub #392) the student's cumulative score — mounted once in `app/layout.tsx`. Score used to be fetched separately inside `AppShell` on every mount; it now lives on the context (`score`, loaded once per sign-in, `null` for an instructor) so every display of it agrees, and `refreshScore()` is the one invalidation path — every play flow that can change the total, MCQ (`app/activities/[slug]/play/page.tsx`) and LLM-graded (`components/LlmPlayView.tsx`) alike, must call it on session completion, since neither the sidebar nor `lib/scoreStore.ts`'s own cache has any other way to learn a just-finished session changed the total. The LLM-graded flow omitting this call used to be exactly the bug (GitHub #392) — keep both play flows' finish handlers calling it if you touch either.

Session renewal is deliberately two-pronged and there is **no guest/placeholder state**: `UserProvider` refreshes proactively on a 45-minute interval, and reactively when `/api/profile` answers 401 — only if `refreshAccessToken()` also fails is the session cleared and `token` dropped to null. A transient fetch error is explicitly *not* treated as an invalid session; keep that distinction if you touch `refresh()`.

Pages gate on role via `lib/useRequireRole.ts` (`useRequireRole('student' | 'instructor')`, GitHub #82). Callers must return `null` while `!authorized` — the redirect happens in an effect, so rendering early flashes the wrong page. The two roles are asymmetric about a missing profile row (normal right after registration): `'student'` lets it through, `'instructor'` does not and redirects to `/profile`. Treat a page's required role as load-bearing — it's what keeps a student off `/instructor/*` and an instructor out of the quiz-taking flow under `/activities/*`.

Instructor role assignment happens in `app/api/auth/register/route.ts`: the request's `instructorCode` is compared **server-side only** against the `INSTRUCTOR_SIGNUP_CODE` environment variable, written into the auth user's metadata (the `"user"` profile row doesn't exist until the profile form is submitted, where `app/api/profile/route.ts` reads the role back out). `INSTRUCTOR_SIGNUP_CODE` must never be hardcoded or committed (GitHub #280) — an unset, empty, or `CHANGE-ME`-prefixed value makes any instructor signup attempt fail with a 500 rather than silently falling back to a built-in default.

Every protected API route then repeats its own preamble: read `Authorization: Bearer …`, `supabase.auth.getUser(token)`, and derive `user_id` from the result — **never** from the body, query string, or path. The `/api/students/{studentId}/*` routes compare the path param against the token's user and 403 on mismatch (no instructor exception on any of them today).

**Onboarding tour.** `"user".has_seen_onboarding_tour` (`supabase/schema.sql`, default `false`) gates a first-login guided tour, read/written through the same `PROFILE_COLUMNS`/PATCH body as every other profile field — no dedicated route. `components/OnboardingTourProvider.tsx` (mounted in `app/layout.tsx`, inside `UserProvider`) auto-starts once per user when `profile.has_seen_onboarding_tour` is false, and PATCHes it to `true` on close/finish. `components/OnboardingTour.tsx` (mounted in `AppShell.tsx`) renders the actual spotlight — a CSS box-shadow cutout positioned against `[data-tour="..."]` targets — walking a student or instructor through a different step list (`lib/onboardingTourSteps.ts`). The profile page's "Show tour again" only resets client state (`setStepIndex(0); setActive(true)`) — it deliberately does not touch the DB flag, so a repeat viewing never looks like a fresh signup to anything else that reads it.

### Session model (the core domain)

- **One in-progress session per (user, activity_type)**, enforced by the partial unique index `uq_session_log_one_active`. `POST /api/sessions` is therefore idempotent: it returns the existing session with `resumed: true` (200) instead of creating a second one, and treats a `23505` race as "someone else started it". "Start" and "resume" are the same call.
- **The current question is derived, never stored.** It is the lowest `position` in `session_to_question` without a row in `answered_question_log` (`nextUnansweredPosition` in `lib/sessionQueries.ts`). Do not add a `current_question_index` column — the absence of a mutable pointer is what makes multi-device resume conflict-free, and it's why `GET /api/sessions/current` is a pure read with nothing to merge.
- **Write before disclose.** `POST /api/sessions/{id}/answers` commits the answer first and reveals `correct`/`explanation` second; `POST .../feedback` only serves a solution for an option already present in `answered_question_log`. Otherwise the endpoints become an oracle for trying options until one is right.
- **The question/prompt pool a session draws from respects the granting assembled quiz's exclusions, for both kinds.** `POST /api/sessions` resolves access via `getAccessibleCourseForActivity` (`lib/activityCourseQueries.ts`), not the plain `checkActivityAccess` wrapper, because the draw needs the returned `assembledQuizId` to filter the catalog's raw question pool through `listQuizExcludedQuestionIds` (`lib/assembledQuizQueries.ts`) *before* both the draw and the `QUESTIONS_PER_SESSION` minimum-count check — an excluded question can no longer be served, and no longer counts toward whether there are enough questions to start a session. `POST /api/activities/{activityType}/llm/sessions` mirrors this exactly on the `user_story` side (`listQuizExcludedUserStoryIds`, checked before both the draw and the `STORIES_PER_SESSION` minimum) — before this, excluding a prompt down below the minimum still let a student start the quiz, drawing from (and getting stuck unable to complete) a pool that looked sufficient before exclusions were applied. Hand-picked extras (`assembled_quiz_extra_question`/`assembled_quiz_extra_user_story`) are not unioned into either live draw; only exclusions are enforced today.
- **Scores roll up in the database.** The `trg_answered_question_log_score` trigger adds to `session_log.cumulative_score` inside the insert's transaction; routes re-read the row afterwards rather than computing the total locally.
- **Column visibility is a query-level concern.** `SESSION_QUESTION_COLUMNS` in `lib/sessionQueries.ts` deliberately omits `is_correct` and `explanation`; only `loadQuestionOptions` (feedback path) selects them. Keep new queries on that split.
- **Option order is shuffled server-side** with `lib/shuffleArray.ts` (Fisher-Yates, not a `sort()` comparator — the biased-comparator version was a real bug, see `__tests__/lib/shuffleArray.test.ts`).
- **A new session starts one level past the highest the student has passed for that activity type**, not always at `START_DIFFICULTY_LEVEL`. `POST /api/sessions` computes this via `findStartDifficultyLevel` (`lib/sessionQueries.ts`), which reduces the student's `session_log` rows with `highestPassedLevelByType` and feeds the result to `nextDifficultyLevel` (both in `lib/sessionRules.ts`) — `min(highestPassed + 1, MAX_DIFFICULTY_LEVEL)`, or `START_DIFFICULTY_LEVEL` if nothing has been passed yet. `highestPassedLevelByType` is also what `lib/titleQueries.ts`'s `computeStudentTitles` reduces over, so a student's title and their next session's difficulty can't disagree. `nextDifficultyLevel` is reused client-side too, by `app/courses/[id]/page.tsx` (the course-scoped quiz list that replaced the old flat `app/activities/page.tsx` list, see above), to show the level a card's next click will actually start at (falling back to a running session's own `difficulty_level` when one exists) instead of a hardcoded level-1 pill that never advanced — see `activityCardStatus.ts`'s `'mastered'` status below. `session_log.difficulty_level` has a `CHECK (difficulty_level BETWEEN 1 AND 3)` constraint mirroring `question`/`user_story`/`title_definition`'s, added after it was noticed missing.
- **A student can also explicitly pick a level to replay, up to the auto-advance ceiling.** `POST /api/sessions` takes an optional `difficultyLevel` (`app/api/sessions/route.ts`); if it's above `findStartDifficultyLevel`'s result the route 403s with `'You have not passed that difficulty level yet.'` — so the reachable range is every already-passed level *plus* the one auto-advance level, never further ahead. `components/LevelReplaySelector.tsx` (rendered on `app/activities/[slug]/page.tsx` only when nothing is in progress — not on the Write Acceptance Criteria page, which has no difficulty progression at all) always renders a fixed `totalLevels` slots (defaulting to `MAX_DIFFICULTY_LEVEL`), not just the reachable ones — anything above `highestSelectableLevel` renders disabled with a lock icon rather than being omitted, so the row's shape doesn't depend on when `attempts` has loaded and `components/ActivityDetailSkeleton.tsx` can match its chip count up front. The Write Acceptance Criteria page uses this same default too, so Medium/Hard render permanently locked there even though it has no progression to unlock. It defaults to the auto-advance level and turns sticky once the student picks one explicitly (`userPickedLevelRef`). `lib/sessionClient.ts`'s `startSession` forwards `difficultyLevel` only when the caller passes one, so a plain "Start" call is unaffected. `app/courses/[id]/page.tsx`'s `ActivityCard` also seeds this from a `?level=` query param on the link into the detail page, avoiding a level-1 flash before the real value loads.
- `lib/sessionRules.ts` holds the shared constants (`QUESTIONS_PER_SESSION = 4`, `START_DIFFICULTY_LEVEL = 1`, `MAX_DIFFICULTY_LEVEL = 3`, `PASS_RATIO = 0.75`, `SESSION_COLUMNS`, `SESSION_STATUSES`) so routes cannot drift apart. Partial credit is a known gap: `scoreForAnswer` is all-or-nothing until `answer` gains a score column.
- Gamification is derived, not stored: `lib/scoreQueries.ts` sums the best *passing* score per (activity_type, difficulty_level); `lib/titleQueries.ts` looks up `title_definition` by the highest passed level per activity type. Nothing about score or title lives on the student row.
- **The "new title earned" toast (REQ-GAM-PL-2.4/2.5) diffs two client-side snapshots, not a server flag.** `app/activities/[slug]/play/page.tsx` fetches `loadStudentTitles` once on mount (`titleAtStart`, captured before the session can possibly finish) and again after a completed session passes; a title only counts as newly earned if the post-session level beats `titleAtStart` (`null` counts as "nothing passed yet"). This is what tells a genuine first-time pass apart from a retake of an already-mastered level — the server has no "was this title new" concept to ask instead. `SessionSummaryScreen`'s optional `titleNotification` prop renders the toast.
- **The level-unlock animation (GitHub #371) is derived on arrival, not handed over.** `components/LevelReplaySelector.tsx` renders every level the activity has — `totalLevels` slots, default `MAX_DIFFICULTY_LEVEL` — with anything past `highestSelectableLevel` disabled and padlocked, which is what gives the animation a closed lock to open. The trigger is *not* a query param or router state from the play page: `handleFinishSummary` force-refreshes the completed-attempts cache and `router.push`es back to `/activities/{slug}`, so `app/activities/[slug]/page.tsx` already has the raised `highestSelectableLevel` in hand and only has to diff it against `lib/unlockedLevelStore.ts`'s per-device snapshot (`newlyUnlockedLevel`, pure and unit-tested). Two consequences worth keeping: the snapshot is re-recorded on **every** visit, not just animating ones, which is what stops `loadCompletedAttempts`'s background revalidation from restarting an animation already in flight; and a `null` snapshot (first visit on this device, or post-logout) deliberately animates nothing, so a level passed on another device is never re-celebrated. Passing `MAX_DIFFICULTY_LEVEL` animates nothing either — `nextDifficultyLevel(3) === 3`, the ceiling doesn't move. The selector stays stateless: `unlockingLevel` is a prop and the clearing timer lives in the page. The padlock SVG is inlined in the selector rather than reused from `components/TitleProgressionTrack.tsx`'s `LockIcon` because styled-jsx only scopes its generated class onto that component's own JSX — a shackle inside a child component would never match the `.lock-shackle` keyframes.

### Reading sessions: which route answers which question

Five read endpoints look similar and are not interchangeable — pick by the question being asked, and keep new ones on the same split:

| Route | Question it answers | Empty result |
|---|---|---|
| `GET /api/sessions?status=…` | "What did I do lately", one status, all activity types | `200` `[]` |
| `GET /api/sessions/current?activityType=` | "Resume this activity" — session + questions + answers so far | `200` with `session: null` |
| `GET /api/sessions/in-progress[?activityType=]` | "Is something running?" — no questions/prompts | `404` *with* activityType, `200` `[]` without |
| `GET /api/sessions/completed?activityType=` | "How did I do at this activity" — attempt history | `200` `[]` |
| `GET /api/students/{id}/activities` | Full timeline: every status, every activity type, merged | `200` `[]` |
| `GET /api/instructor/activities` | Same timeline, scoped to catalogs the instructor created, `+ studentId`/`studentName`/`ownedActivityTypes` | `200` `{ sessions: [], ownedActivityTypes: [] }` |
| `POST /api/activities/{activityType}/llm/sessions` | Start/resume an **LLM-graded** activity — the free-text twin of `POST /api/sessions` | 400 unless the type is `llm-graded` |
| `GET /api/activities/{activityType}/llm/sessions/current` | Resume it — session + prompts + submissions so far | `200` with `session: null` |

(`GET /api/students/{id}/history` is the completed-only, cross-activity variant of the second-to-last one, per REQ-PL-3.1. `GET /api/instructor/students/{id}/history` is that same route's instructor-facing counterpart — identical columns and ordering, gated by `requireInstructor` instead of a `studentId === caller` check, and its own 404 for an unknown `studentId` since the caller didn't just authenticate as them.)

The instructor route is the one read that deliberately returns rows the caller doesn't own, which is why `requireInstructor` runs before any query and why its `loadAllStudentActivity` filters the joined `"user"` row on `role = 'student'` with an **inner** join — a non-inner join would null the embed instead of dropping the row, and instructors would appear in their own report. Only students who have attempted something appear at all; the roster is derived from attempts, so an enrolled student with zero sessions is invisible (known gap, separate story). Unlike the two routes below, `GET /api/instructor/activities` (GitHub #171) is scoped to catalogs the caller created — `creator_id = guard.user_id` via `listOwnedActivityTypeSummaries` (`lib/activityTypeQueries.ts`) — not every catalog in the system; every student is still visible on those catalogs, so it's "my catalogs, all students" rather than "my students, all catalogs." That same call also returns `ownedActivityTypes` (every catalog the instructor owns, both grading kinds, whether or not it has any attempts yet) so the Instructor Dashboard's stat cards (GitHub #171 follow-up) can render a real card — with `'—'` placeholders — for a just-created, zero-attempt catalog instead of only inferring ownership from `sessions`; `entries.length === 0 && ownedActivityTypes.length === 0` is the actual "nothing to show at all" check on `app/instructor/page.tsx`, not a bare empty-`sessions` check. `GET /api/instructor/sessions` and `GET /api/instructor/statistics` (class average + pass rate per quiz, `lib/quizStatisticsQueries.ts`, GitHub #114) are guarded the same way but stayed class-wide across catalogs: both currently treat "every quiz" as every row in the `activity_type` table and "every student" as every `role = 'student'` account, with no `courseId` filter and no creator-ownership filter either (same gap as #115's "students of the current prof") — this is a routes-don't-consume-it gap, not a schema gap: `course`/`student_course` (REQ-DL-5, see the Courses paragraph above) already model instructor-owned classes, these routes just don't scope by them yet.

### Client-side caching

Twelve stores — `lib/scoreStore.ts`, `completedSessionsStore.ts`, `completedAttemptsStore.ts`, `activityLogStore.ts`, `instructorActivityStore.ts`, `instructorStudentsStore.ts`, `acceptanceCriteriaSubmissionsStore.ts` (one of two places that kept the old `acceptanceCriteria*` naming when GitHub #379 renamed the rest to `llmActivity*` — the other is the `/api/instructor/acceptance-criteria/*` route paths), `instructorLlmConfigStore.ts`, `leaderboardStore.ts`, `leaderboardCoursesStore.ts`, `previousRankStore.ts`, and `unlockedLevelStore.ts` — are a *different* kind of web-storage use from `activityStore.ts`: not mocks, but caches in front of real API calls. All share one shape: a versioned key, SSR-guarded read/write, only typed getters/setters exported (never the raw store), keyed by `studentId`/`instructorId` — `completedAttemptsStore` additionally by `activityType`, `instructorLlmConfigStore` by `provider`+`model`, `leaderboardStore` by `courseId`. `sessionClient`'s (and `studentCourseClient`'s) loaders take an optional id to opt into the cache and a `forceRefresh` flag to bypass and re-cache it. Copy this shape for any new cache, and add a `clearCached…()` to it (see below). Ten of the twelve are `localStorage`; `leaderboardStore` and `leaderboardCoursesStore` are `sessionStorage` (see the leaderboard paragraph above for why) — `previousRankStore` stays `localStorage` despite living in the same feature, since a rank *delta* is only meaningful measured against the last real visit, restart or not. `unlockedLevelStore` is the same "snapshot of last time" shape as `previousRankStore` rather than a response cache: it records the highest selectable difficulty level a student had *seen* per `(studentId, activityType)`, so `app/activities/[slug]/page.tsx` can diff against it and fire the GitHub #371 unlock animation exactly once (see the Session model section). (`lib/instructorQuestionsStore.ts` was a twelfth, fronting the now-deleted flat Question Bank page's `GET /api/instructor/questions` — removed in GitHub #359 along with that page, since the catalog detail page it was replaced by isn't cached; see the Question Catalogs paragraph above.)

The invalidation rule differs: score and completed-sessions only change when a session *completes* (the play page's `handleContinue` refreshes them there), but `activityLogStore` also contains in-progress and abandoned sessions — anything that starts, answers, or abandons must `forceRefresh` it too. `instructorStudentsStore` and `acceptanceCriteriaSubmissionsStore` need no invalidation at all (their own header comments say why).

`loadCompletedAttempts` (`completedAttemptsStore`) was the first loader that wasn't purely cache-first (GitHub #333): a cache hit still resolves immediately, but it also fires the network request in parallel and, if an optional `onRevalidate` callback was passed and the server's answer actually differs from what was just returned, hands the fresh rows back through that callback — a same-device reload re-fetching identical rows causes no re-render. This exists because nothing on the current device has any reason to invalidate this cache when a session completes on a *different* device. `loadStudentScore` (`scoreStore`) picked up the identical `onRevalidate` shape afterward (GitHub #392 follow-up) for the same reason — a score that changed in another tab/device/browser profile has no local trigger to invalidate it otherwise — and every caller that reads score for display (`UserProvider`'s own load, `MasteryProgressSection`, `app/students/[id]/page.tsx`'s own-profile branch) now passes it. Every other store in this section still stays strictly cache-first-then-`forceRefresh`; don't copy the `onRevalidate` pattern onto a new store without the same cross-device staleness problem. `app/activities/[slug]/page.tsx`'s own call to `loadCompletedAttempts` is a second, opposite deviation from the general rule: it passes `forceRefresh: true` outright rather than using `onRevalidate`, because `highestSelectableLevel` there is derived straight from `attempts` — a stale cache hit wouldn't just show a stale value, it would change `LevelReplaySelector`'s locked/unlocked button shape on that same render.

`loadInstructorActivities` (GitHub #176) *is* cache-first, via `instructorActivityStore.ts` keyed by `instructorId` — but unlike the student-scoped stores, nothing the instructor's own tab does can invalidate it, since the underlying list changes whenever *any* student answers something on one of the instructor's catalogs and the instructor's tab never learns about that. Its only invalidation is manual: the instructor dashboard's Refresh button (`app/instructor/page.tsx`) calls it with `forceRefresh: true`. A freshly mounted dashboard is otherwise cache-first and can render stale data until that button is clicked. The cached value is `{ sessions, ownedActivityTypes }`, not a bare array — the store bumped its key from `rc_instructor_activity_v1` to `_v2` when `ownedActivityTypes` was added (GitHub #171 follow-up) rather than reshaping the old value in place, so a stale v1 entry is simply never read again instead of being misread as the new shape; `isCachedInstructorActivity` guards the read against exactly that mismatch.

**Logout clears all twelve.** `lib/clientCaches.ts`'s `clearAllClientCaches()` is called from `clearStoredAccessToken` (`lib/authClient.ts`), so both ways a session ends are covered — the explicit `signOut()` and `UserProvider` giving up after a failed refresh. This matters beyond staleness: `instructorStudentsStore`, `instructorActivityStore`, `acceptanceCriteriaSubmissionsStore`, `leaderboardStore`, and `previousRankStore` hold *other people's* names, answers, grades, usernames or ranks. `lib/activityStore.ts` is deliberately excluded — it is the only copy of the student's level/best score/title, so clearing it would be data loss, not cleanup.

### Database

`supabase/schema.sql` is the single migration (plain DDL, no `IF NOT EXISTS` — its footer documents the drop/rename paths for re-running). Notable: the profile table is `"user"` (a reserved word — quoted in SQL, plain `.from('user')` in supabase-js) and FKs to `auth.users`; the question-bank tables have **RLS enabled with no policies at all**, so they are unreachable except through a service-role route. Adding a table the client must not read directly should follow the same pattern. `session_log`/`answered_question_log`/`submission`/`"user"` do have own-row policies, but every data route uses the service-role client and bypasses them — the route, not the database, is what enforces scoping. `title_definition` still has no RLS (known gap, noted in the RLS block).

Indexes worth knowing before adding a query: `ix_session_log_user_id` and `ix_session_log_ended_at` (the latter matching `loadAllStudentActivity`'s two-column `ORDER BY` exactly) back the class-wide instructor reads, and `ix_user_role` backs their `role = 'student'` inner join. The partial `uq_session_log_one_active` only covers in-progress rows and can't serve a general scan.

**Timestamps are zone-less.** `started_at`, `ended_at`, `submitted_at`, `graded_at` and `updated_at` are all `timestamp` (not `timestamptz`), so PostgREST returns them without an offset and `new Date()` misreads them as local time. `lib/dateTime.ts`'s `toInstant()` pins them to UTC at the three client boundaries (`toActivityLogEntry`, `loadCompletedAttempts`, `loadInstructorACSubmissions`). Any new query handing a timestamp to the UI must route it through `toInstant` too — the real fix would be changing the column types.

`activity_type` is a real lookup table (GitHub #122/#123), with `question`/`session_log`/`title_definition` FK'd against it — but it is no longer a fixed set of three: instructors can add rows to it at runtime (GitHub #347; see the custom-quizzes bullet above). `lib/activityTypes.ts` reflects this — `isActivityType` is an async DB check, not a lookup against a compile-time array — so `supabase/seed.sql`'s `question.activity_type` rows are just the three built-ins every fresh deployment needs seeded, not the complete valid set.

No schema-only, not-yet-wired additions remain as of GitHub #380: `activity_type.grading_kind` (wired by #379) and `assembled_quiz_extra_question` (wired by #380, see the Assembled quizzes composition section above) were the two that used to be flagged here.

### Tests

Vitest, `environment: 'node'`, glob `__tests__/**/*.test.ts`, no React/DOM tests — the mock-backed instructor UI and the localStorage stores are untested by design.

Route tests (`__tests__/api/`) mock `lib/supabase` with a `vi.hoisted` fake whose `from(table)` returns a chainable builder — `select/eq/in/order` are no-ops, and the builder is *thenable* so queries without `.single()` resolve too. Results are **queued per table** (`queue('session_log', { data, error })`) and shifted in call order, and the mock records `inserts`/`deletes`/`tables` for asserting what the route did. Route handlers are imported directly and invoked as `POST(new Request(...), { params })`.

Pure-helper tests (`__tests__/lib/`) skip `vi.mock` entirely — `requireInstructor` takes its Supabase client as an argument precisely so its test can pass in a locally built fake. Prefer that shape for new helpers.

When adding a route, copy the harness from the nearest existing test rather than inventing a new mocking style.

## Styling Guidelines

Tailwind CSS is the single, project-wide approach to styling — no CSS Modules, styled-components, or component libraries. Every page and component styles exclusively through Tailwind utility classes.

**Design tokens — the source of truth:**
- Brand colors are defined once as CSS custom properties in `app/globals.css` (`:root`, prefixed `--rc-*`), then exposed as named Tailwind colors under the `brand` key in `tailwind.config.js` (`theme.extend.colors.brand`). Use these tokens (`bg-brand-navy`, `text-brand-purple`, `border-brand-navy-border`, …) instead of writing raw hex values like `bg-[#7C4DFF]`.
- Available tokens: `brand-navy` / `brand-navy-2` / `brand-navy-border` / `brand-void` (dark surfaces), `brand-purple` / `brand-purple-dark` / `brand-purple-glow` (primary accent), `brand-teal` / `brand-teal-dark` / `brand-teal-ink` (secondary accent), `brand-gold` / `brand-gold-dark` (rewards/XP/achievements only), `brand-green` / `brand-green-dark` (success/passed states), `brand-danger` / `brand-danger-light` (errors, destructive actions), `brand-ink` / `brand-ink-muted` (text on dark surfaces).
- For the light/white content areas (inside `AppShell`'s `<main>`), use Tailwind's built-in gray scale (`text-gray-500`, `bg-gray-50`, `border-gray-100`) rather than inventing new grays.
- Border radius: use `rounded-brand-sm` (9px, small icon buttons), `rounded-brand-md` (10px, inputs/buttons/nav items), `rounded-brand-lg` (20px, cards/panels), or Tailwind's built-in `rounded-full` (pills, avatars). Don't add new arbitrary `rounded-[Npx]` values.
- Spacing: use Tailwind's default spacing scale (`p-4`, `gap-2.5`, `mb-5`, …) — no arbitrary pixel spacing.
- Typography: the font family is set once in `app/globals.css` (`body { font-family: ... }`). Don't override `font-family` in individual components.

**Rules for new pages/components:**
- No inline `style={{ ... }}` for anything expressible as a Tailwind class. Inline styles are only for genuinely dynamic, per-instance values (e.g. per-sparkle animation offsets in `components/PasswordField.tsx`).
- No new raw hex colors in `className`. If a needed color isn't in the `brand` palette yet, add it as a `--rc-*` variable in `app/globals.css` and a matching token in `tailwind.config.js` first, then use the token.
- Reuse existing shared components before writing new markup: `components/AppShell.tsx` (page shell/nav for authenticated pages; it branches its nav on `profile?.role`), `components/ActivityCard.tsx`, `components/QuestionCard.tsx`, `components/FeedbackCard.tsx`, `components/PasswordField.tsx`, `components/Avatar.tsx` (the round avatar-or-initials circle for dark surfaces — sizes are a fixed `sm`/`md`/`lg`/`xl` set, not a free className; not for `app/profile/page.tsx`'s own upload-button avatar), `components/StatTile.tsx` (one labeled stat number), and on the instructor side `components/ActivityLogTable.tsx` / `ActivityLogRow.tsx` (shared with the student activity log), `InstructorStudentCard.tsx`, `QuestionFormModal.tsx`, `CourseCard.tsx` (styled to match `InstructorStudentCard.tsx`), and for LLM-graded catalogs `PromptFormModal.tsx`/`CatalogPromptCard.tsx` (the free-text counterparts to `QuestionFormModal`/the inline question markup). Difficulty-level labels for any authoring form come from `lib/difficultyLevels.ts`, not a local copy. The student-side course browse/join card, `StudentCourseCard.tsx`, is a deliberately separate component from `CourseCard.tsx` — same visual language, different audience/data, not a shared component. Prefer extending one of these over duplicating its markup.
- **Modals share behavior, not markup.** `components/useModalDismiss.ts` owns the focus trap, Escape-to-close, initial focus and restore-focus-on-close that every popup here used to hand-roll (`QuestionFormModal`, `EditCourseModal`, `DeleteCourseModal`, `DeleteQuestionModal`, `CreateCourseModal`, `CreateCatalogModal`, `CreateQuizModal`). Use it for any new modal — in particular its `isBlocked` argument, which suppresses dismissal during an in-flight save and is passed as an effect *dependency*, fixing the stale-closure bug every hand-rolled copy has. It is deliberately behavior-only: each modal still composes its own overlay/panel/header markup, because their bodies genuinely differ.
- Custom CSS animations that Tailwind utilities can't express (`@keyframes`, gradient-text glow, etc.) use `<style jsx>` (styled-jsx, built into Next.js) scoped to the component — see `app/dashboard/page.tsx` and `components/PasswordField.tsx`. Reference the `--rc-*` variables inside these blocks instead of hardcoding new hex values, so raw CSS and Tailwind classes never drift apart.

**Known gap:** existing pages/components still contain literal arbitrary-value classes (e.g. `bg-[#7C4DFF]`) that predate this token system. New code should use the `brand-*` tokens above; migrating existing files onto the tokens is a separate follow-up, not required for this to take effect going forward.
